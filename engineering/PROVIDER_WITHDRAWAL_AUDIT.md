# Provider Withdrawal Audit

本文记录 owner-bound runtime capability 在 provider withdrawal、generation stop 和 cached handle 场景下的当前事实。它是维护者审计入口，不是 Plugin 作者 API，也不引入新的 public lifecycle hook、错误 contract 或 capability primitive。

本文延续 [`SPATIOTEMPORAL_COMPOSABILITY_NOTES.md`](SPATIOTEMPORAL_COMPOSABILITY_NOTES.md) 中的 capability withdrawal 思考。结论截至 2026-08-19：还没有足够证据抽取统一 `GenerationLease`；各 capability 应继续保留自己的 owner/admission/cleanup 语义，并用测试锁住差异。

## 审计词汇

| 词汇                   | 含义                                                                                     |
| ---------------------- | ---------------------------------------------------------------------------------------- |
| publication withdrawal | 从 registry、route table、layout/grant 或 catalog 中撤销未来 discovery/lookup。          |
| owner admission close  | owner generation 停止接纳新的 capability operation。                                     |
| accepted work drain    | 停止时等待已经接纳的 operation、invocation、setup 或 task 进入 settle。                  |
| root resource          | runtime root 拥有的长期资源，例如 command catalog、HTTP root app、database backend。     |
| generation handle      | 绑定某个 plugin Context/generation 的 service view、registration、route 或 data handle。 |
| manual dispose         | 显式撤销单个 publication/registration；它不必等价于 owner generation stop。              |

## 当前设计结论

不要在这一阶段抽取 public 或 internal `GenerationLease`。原因是 capability 之间有真实差异：

- commands 需要 owner invocation gate，并在 stop 时 abort 已接纳调用；
- HTTP route withdrawal 只撤销未来 route lookup，不取消已进入请求；
- database 不强行 abort 已接纳 transaction，而是等待运行中和排队 operation settle；
- worker task 可以用 owner signal 取消 queued/running CPU work；
- Workbench grant revocation 是 publication/authorization 失效，不等于每个 RPC method 的运行时取消；
- cache 和 rates 都绑定 caller/provider generation，但 in-flight 语义仍不相同：cache 迟到 continuation 会在 active check 处失败，rates 已提交 backend 判定允许 settle。

后续只有在多个已实现 capability 证明重复了同一套状态机，并且抽取能删除代码、统一错误和增加测试覆盖时，才重新评估 internal primitive。任何 primitive 都不得把 root-owned durable resource 和 generation-owned handle 合并，也不得把当前 Plugin 作者 API 扩大成新的 lifecycle hook。

## 后续测试债

- commands：manual registration dispose、retained installed handle、compatible replacement 与 incompatible fail-closed 已覆盖；后续只需按真实 carrier 补协议投影测试；
- HTTP：plugin stale handle、host same-id stale disposer 和 in-flight fetch 已覆盖；后续只需按新 route 入口补同构测试；
- database：已覆盖 accepted operation drain 和 cached handle stop；若实现真正需要取消 queued operation，应另立设计并修改测试；
- Workbench：RPC method 在 grant revoke / owner stop 后的 in-flight settle、events browser disconnect 与 owner stop 组合 cleanup、detach 后迟到 send 丢弃已覆盖；后续可补 liveQuery variant 回收与 owner stop 的交错 trace；
- Node module：source binder detach、pending update 和 owner stop 组合 trace 已覆盖；后续可补多 consumer 共享 declaration 的 detach 顺序；
- cache/rates：若后续强化 Redis adapter lifecycle 或真正的 same-slot backend replacement harness，再补 adapter-level stale handle 与 in-flight integration trace；不要把它们折叠成同一个抽象 lease。
