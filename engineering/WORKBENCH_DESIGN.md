# Workbench 交互设计决策

修改 Shell 导航、目录、标签、工具面板或视觉层次时，从本页开始。本页拥有设计理由和评审准则；操作说明见[使用工作台](../docs/workbench/operations.md)，状态与源码所有者见 [Frontend](FRONTEND.md)，发布/API 边界见 [Workbench 架构](WORKBENCH.md)。不把历史提案或截图当作当前契约。

## 先确定用户任务

工作台服务两种任务：管理插件的运行、配置与依赖；使用插件发布的业务应用。它们共用工作区，但导航不能互相冒充。

每次设计先写清用户正在处理的对象、下一步操作和需要同时参考的信息。默认让用户在当前文档继续工作；只有需要并排比较、保留另一份页面输入时才显式创建文档。不要通过自动增加标签、永久增加侧栏或新增一套管理目录解决局部导航问题。

判断效率看完成任务需要多少寻找、切换、滚动和重复输入，不以屏幕塞满、组件数量或代码行数衡量。紧凑的行必须仍能辨认、聚焦和操作；完整名称与失败原因必须有可达入口。

## 页面与区域怎么选

| 用户需要             | 设计选择                           | 原因与边界                                                          |
| -------------------- | ---------------------------------- | ------------------------------------------------------------------- |
| 全局入口             | 官方入口栏；应用进入应用目录       | 插件不无限扩张一级图标栏；入口栏支持图标或图标加文字                |
| 管理插件             | 唯一插件目录 + 中央详情            | 分组、排序、多选和拖动沿用同一份目录模型，运行状态只是筛选条件      |
| 使用业务能力         | 独立应用路由，应用内部组织对象列表 | bot、会话等领域对象不是新的插件管理入口                             |
| 独立阅读、编辑、比较 | 中央文档                           | 有自己的地址、输入、离开守卫和打开资源                              |
| 当前插件的辅助上下文 | 左、右或底部 panel                 | 跟随活动文档的 exact owner，包括 fork；不创建文档路由或独立传输连接 |
| 临时低频设置         | 按钮打开菜单或浮层                 | 不长期占用阅读空间；日志策略放在日志区域的插件名称旁                |
| 多插件共用业务列表   | 领域聚合插件 + 来源插件 API        | Shell 不理解 bot schema，也不建立无领域契约的通用集合注册表         |

多个插件共用列表的完整例子见[组合与多来源列表](../docs/workbench/composition.md)。列表行是领域数据，不为每一行创建 publication 或 socket。用真实 Workbench API 验证状态、选择与 owner 释放，纯前端假数据不能证明扩展契约成立。

## 导航和文档不变量

普通入口始终在活动文档内导航；无活动文档才新建。右侧“最近日志”中的“查看完整日志”是显式并行排查入口，打开按当前 canonical owner 筛选的独立日志文档，保留原配置上下文。活动标签后的 `+` 复制当前已提交地址和名称，创建独立文档，不复制未保存草稿。菜单复制遵循同一语义。显式插件 API 打开文档是另外一个明确操作，不改变普通浏览的默认行为。

默认名称表达当前内容：插件详情显示插件名，发布页面使用声明标题。手动重命名不应被查询变化、后台刷新或重新聚焦覆盖；换到另一页面身份时采用其名称。地址栏跟随活动文档，点击工具不能把它变成工具地址。

离开、批量关闭和重置都经过文档守卫；拒绝关闭不能先删布局再尝试补救。布局持久化不等于保存草稿；失败快照保留并给出显式恢复入口，不悄悄回退默认布局伪装成功。

## 工具布局的当前选择

FlexLayout 原生模型是唯一几何与标签状态来源，Worksplit 负责文档与布局操作的衔接。不要另建一份坐标、选中标签或拖动模型。

中央文档可以分屏、移动和分组。官方目录和右侧官方工具提供稳定入口，固定且不能关闭；右侧官方“插件面板”内部只切换“插件信息”和“最近日志”。插件扩展不混入官方内部标签，而是按声明区域成为独立原生 Border 标签，可关闭、重新打开和在本区域内排序，不能跨区域或拖入中央文档。

插件面板默认按需打开，避免每个插件自动铺满侧栏。官方“插件信息”的扩展列表与顶部查找使用同一份当前 owner 声明和打开路径；重复打开聚焦现有面板。入口可发现性来自声明，而非当前已打开标签，因此关闭后仍能找回。停止插件或撤回声明不能伪装成可打开入口。

收起、关闭和切换上下文是三种行为：收起保留标签作为恢复入口；关闭移除插件标签并释放资源，刷新不会重新补回；切换插件卸载旧资源，但保留该 owner 未关闭标签的布局，切回时恢复。没有适用内容的区域不占位。底部没有官方默认工具；左边只有官方目录时隐藏重复竖条，有插件标签时显示原生标签条。

几何与选择仍由一个 FlexLayout Model 拥有。面板不改变中央地址；业务草稿不能依赖临时工具一直挂载。持久化与失效处理只维护在 [Frontend](FRONTEND.md#插件上下文与面板资源)，不要让 UI 组件各自保存一套“已打开插件面板”。

## 目录与批量操作

用户分组表达工作组织；插件依赖图、publication 分类和文档标签组各有不同含义，不能互相替代。分组数据所有权与同步协议见 [Plugin Catalog](PLUGIN_CATALOG.md)。

点击名称浏览，明确的选择按钮或修饰键选择，选择不能顺带打开页面。范围选择、方向键和全选只作用于当前可见展开行；既有选择是否保留与本次操作范围是两回事。按钮、输入框和拖动手柄保留自己的键盘行为，容器快捷键不能劫持子控件。

拖动必须表达将移动哪些项、目标组与落点；复用已有批量移动/排序语义，不用另一份视觉列表重新实现管理器。常用操作可直接触达，低频操作集中在菜单。不要靠立即弹出的悬浮大卡片提供必要信息：滚动期间不弹提示，延迟提示只补足名称与简短状态，详细诊断由详情承载。

## 阅读层次

视觉层次帮助用户辨认当前位置、选择和下一步，不靠更多卡片或更小控件提高密度。先消除重复内容与空区域，再调整布局；选中、悬停和键盘焦点应能同时辨认。尺寸、表面和交互状态的实现规则统一维护在 [视觉规则](../packages/workbench/shell/color-design.md)。

加载、空、失败和未报告是不同状态；显示“运行中”需要运行事实，更新批次提交不能冒充每个插件启动成功。错误应留在对应文档或区域并提供可行下一步，不把整个工作台变成空白。

## 如何决定删除或放开限制

先区分数据与资源约束、当前交互选择、实现偶然结构。前者必须由权威所有者执行；交互选择需要对应具体任务，允许在新需求下调整；无调用方的模式、不可达状态及为旧实现补洞的说明直接删除。

例如改变插件面板的拖动范围之前，应明确恢复入口、owner 跟随及原生 Border 关系；仅修改 `enableDrag` 会保留另一层放置限制，形成表面可拖却无法落点的行为。原生属性控制交互，放置策略也校验派发与恢复，两者职责不同。不要为了少几个布尔值丢失边界，也不要把当前限制抄进每个组件 README。用户界面只说明可执行操作与必要后果。

## 修改与验收路径

1. 从用户任务选上表中的一种承载方式，列出保留的导航、选择、资源和失败不变量。
2. 从 [Frontend](FRONTEND.md) 找到状态所有者，检查实现、测试和真实调用方。优先删掉已废弃的分支，不增加第二条默认路径。
3. 修改相关实现与对应公开用法；理由变更才修改本页，API 变更更新 API 所有者。包内 README 只负责定位。
4. 按[验收指南](WORKBENCH_FLEXLAYOUT_VALIDATION.md)验证实际路径。视觉变更检查截图，生命周期验证真实发布与释放，文档检查入口和链接。一次截图不证明多窗口、全部浏览器或长期稳定性。

评审时问：首次进入能否找到对象和下一步？日常浏览是否增加无用标签？工具是否能收起并找回？键盘与滚动是否被抢占？分组和选择是否可预测？错误是否保留原始事实？后续 agent 能否从本页找到唯一状态所有者和相应证据？有一项回答不清楚，先修清楚，不用更多装饰掩盖。
