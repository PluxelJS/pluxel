# 面向 Coding Agent 的配置与 Host 控制

状态：待实施。本文确定方向与验收范围，新增接口和制品尚未实现。当前行为仍由 [Config](../CONFIG.md)、[Dev Console](../DEV_CONSOLE.md) 和 [Application Build](../APPLICATION_BUILD.md) 维护。

## 目标与现有基础

让 agent 用普通 TypeScript 发现插件、读取配置、构造修改、校验并提交，再读取实际采用结果。文件用于保存脚本、审查差异和版本管理；配置存储格式按宿主需要选择，本轮不统一为 JSON，也不要求直接编辑内部存储。

现有配置由 Host 私有 SuperJSON 文档保存，Schema、原始输入、已验证输出和运行采用版本已有明确分工。`dev.config`、`dev.plugins` 已委托 Host；[Management](../../packages/services/src/management/web/management-target.ts) 已有基于地址的配置与生命周期接口。主要缺口是脱离 Vite 的可编程控制入口、远程连接，以及不启动应用的完整配置校验。

## 控制方式

默认让 agent 在客户端执行 TS，通过类型化 API 操作运行中的 Host。Workbench、CLI 和 agent 复用相同的 Host 操作与结果类型。

```text
agent TS / CLI / Workbench
          ↓ 本地或远程控制通道
Host：catalog 查询、配置校验与提交、插件生命周期
          ↓
当前实例、持久化后端、已安装服务
```

| 所有者           | 职责                                                          |
| ---------------- | ------------------------------------------------------------- |
| Core / Host      | 插件身份、Schema、配置合成、revision、持久化与生命周期结算    |
| 控制接口与客户端 | 能力发现、输入校验、连接与授权、结构化结果及操作回执          |
| 应用启动器       | 安装和关闭控制入口，发布应用状态，将操作绑定到当前 Host epoch |
| Vite 适配        | 开发期源码加载、共享模块图、更新屏障与 HMR 批次控制           |

基础操作覆盖插件发现与状态、配置 get/validate/patch/reset、启停和重启、有界日志查询。优先复用已有 Management 协议和 Host 实现，基础控制能力独立于 Workbench UI。控制入口显式安装，关闭时不创建 listener 或后台资源。

本地连接可沿用私有 socket；远程连接需要明确的认证和操作授权，不能直接把现有可信本地代码执行端点公开到网络。远程协议只传可序列化地址、输入和结果；插件实例、Context、SDK 对象保持在宿主内。业务方法通过有意公开的调用接口接入。

上传代码到服务器执行作为后续独立能力，适用于需要服务器持有整个任务的场景。首轮客户端脚本即可组合控制操作；现有 Vite 同进程脚本能力继续由开发适配维护。客户端脚本与多个远程调用不构成全局事务。

## 单文件制品与寻址

以多个插件打包为单文件、删除源码并搬离工作区后的应用为基本验收场景。

构建保留 canonical definition address、依赖和配置 metadata，Host catalog 持有地址到实际定义与 Schema 的映射。操作使用现有 `PluginNodeAddress`，default/fork 分别寻址，Part 配置归 owning node。源码路径在地址中只是逻辑身份，客户端无需在部署机器上 import 该路径；压缩后的 class name 和 chunk 文件名不参与寻址。

服务器执行当前制品中的完整校验与生命周期逻辑。客户端类型和字段描述可由构建生成，并标明对应的契约版本与制品摘要；摘要用于检查适配关系，不进入插件身份。远程客户端无需安装插件实现，也不恢复打包前的模块命名空间。

插件 restart 使用当前已接纳的定义。部署新制品与 Vite 源码更新分别沿自己的更新路径执行。

## 配置声明、表单与代码修改

保留 `configs.use(Schema)`、Valibot 和 `formMeta()`。同一份 Schema 提供类型、默认值、完整校验和表单描述；生成描述能表达的约束范围需要明确，完整校验仍使用原 Schema。

每次查询说明 managedInput、effectiveInput、校验输出、来源与覆盖路径，以及保存和采用版本。agent 与 Workbench 都修改原始输入，默认值和 transform 输出保持派生结果。语法错误、未知字段和跨字段失败应提供稳定 code、字段路径及可取得的源码位置；封闭对象拒绝未知键，开放字典按声明接受业务键。

代码中的声明值、部署输入和可管理记录继续按明确规则合成。需要动态管理的字段交给可管理层；程序控制的字段展示来源和覆盖关系。例如 bundle 内声明 `concurrency: 8` 且采用 `declared-first` 时，patch 保存的 `16` 可能被遮盖，结果必须说明实际有效值。修改已编入制品的表达式需要更新部署。

IaC 脚本显式声明自己管理的节点和字段，读取当前值后计算差异，以版本条件提交。重复执行相同目标应收敛为无变化；省略字段保留原值，删除通过显式 remove/reset 表达。脚本管理范围与 Workbench 编辑范围必须清楚，同一字段由声明脚本接管时，表单应引导修改其输入或明确报告接管关系。

## 校验、计划与采用结果

在线校验使用当前 Host catalog。离线校验提供独立库入口，CLI 调用同一实现；输入由调用方显式提供，不执行应用工厂、Plugin init、服务准备或监听端口。

构建从同一声明生成可独立加载的完整校验制品，包含节点绑定、Plugin/Part 配置组合与版本信息。Schema 及其依赖需能独立求值，校验要求确定性；网络连通性和凭据有效性探测属于显式 preflight。缺失动态插件契约、必要环境输入或无法独立加载的 Schema 必须报告校验不完整。JSON Schema 和类型声明只提供辅助提示，不能替代可执行校验。

计划展示输入差异、覆盖来源、受影响节点及尚需在线确认的条件，并绑定输入、Schema 版本和读取基线。提交时重新核对目标和基线，再进入现有 coordinator。多节点操作按实际提交边界报告部分结果。

保存确认、desired 接纳、运行中 applied 分开报告，保留 `saved-not-applied` 与失败原因。异步操作回执绑定部署、实例和 run；Host 替换、断线、取消或超时后继续查询原操作，不自动重投。取消关闭后续接纳并等待已开始的操作结算，已经发生的副作用按真实结果返回。

## Vault

把部署凭据的 owner、namespace、key、Schema 和来源引用纳入可发现、可校验的部署声明。优先沿用现有 env/file 只读绑定与 Vault 服务；普通配置查询、计划、回执和日志只暴露引用、可用性及诊断。

具备权限时在凭据边界校验实际值，缺少读取或解密权限时明确报告值未验证。来源绑定的变更说明何时生效；当前绑定在 Host 创建时固定，需要重建的修改应明确报告。

OAuth 刷新令牌等动态记录继续由 Vault 管理，保留 revision、batch 和 watch；声明应用只影响自己管理的绑定。密钥轮换、加密文件格式和外部 Secret Provider 扩展分别遵守其资源与权限边界。

## 实施顺序与验收

1. 抽离 Vite 无关的 Host 控制接口与客户端，复用现有操作和报告，接通原生应用及远程通道。单文件应用搬离工作区、删除源码、关闭 Workbench 后，仍能发现插件、校验和 patch 配置、读取采用结果、重启节点并查询日志。
2. 生成独立配置校验制品，接入脚本和 CLI。相同契约与输入在线/离线得到一致结果；Part、fork、字段拼写、缺失环境输入、旧版本客户端和冲突都有明确诊断。重复声明无变化，Workbench 与脚本并发修改不会静默覆盖。
3. 接入 Vault 部署声明和脱敏计划。验证引用、权限不足、绑定需重建、并发更新，以及动态令牌不会被声明应用覆盖。

控制接口还需覆盖断线后查询、重复请求、Host epoch 变化、取消与部分失败。实现时同步公开文档、模板和已有调用方；若改变本地存储契约，采用显式一次性转换。

待实施前确定：公共客户端的归包与已有 Management Cap’n Web 接口的复用方式；声明脚本的字段归属记录与表单交互；校验制品的发布入口、完整性与独立加载约束。服务端代码执行待具体任务证明需要后单独设计。
