# Native 与 Vite 执行重构实施记录

状态：已完成实施与三路独立复核（2026-10-05）。保留原路径作为必要决策与证据索引；当前 API 由 `docs/` 和所属工程文档维护。本文件不再提供待实施 API 或另一套启动规范。通过结果、上游声明失败和未验证边界见[部署验证](../HOST_DEPLOYMENT_VALIDATION.md#native-modules-与-vite-生产执行)。

## 已落地的边界

`@pluxel/host-dev` 已改为 `@pluxel/host-vite`，公开入口为根、`/run`、`/console` 和必要 `/internal`。旧 source session、低层 Host 文件执行、framework facades、restart-required 协议、旧执行分类与 scope reader 已删除，没有兼容 alias 或在线格式修复。create 模板保留来源声明，默认 modules + native，并提供独立生产 Vite 配置；参考 Host 保留实际 Package Manager 与服务/启动策略。

## 实际证据要求的修正

1. **pnpm 安装不能原地覆盖。** 真实 A/B/P 样本证明必须同时保留旧字节和共同 P 的物理身份。实现采用 private revision + pnpm global virtual store，不是每轮复制整个隔离 node_modules；未变包的外层 wrapper、物理目标、inode/mtime 不动。权威状态只有 `published-installation.json`，损坏输入显式失败，失败发布不宣称 activation 成功。
2. **固定 imports 必须在共享绑定内加载。** 独立 tarball 安装证明，同版本 Services 因 pnpm peer 组合不同也会有两份 token。原提案的 factory 参数已经提前求值，无法事后绑定。`runHostApplication(entry, { startup, sharedPackages })` 改为预编译模块路径；先创建 scope，再加载默认工厂及固定插件，最后扫描来源。已在 scope 外求值的 entry 明确拒绝。standalone 已内联完整闭包，直接复用 `resolveHostApplication/createHost/prepareHostApplication`，不走模块发现。保留原函数名，没有 factory 兼容重载或 facade。
3. **发布 entry 不代表其所有旧依赖都变化。** 整个旧闭包失效会重复求值 P 并重启无关 B。改为比较已求值依赖的字节基线，只失效实际变化与 importer 传播；普通 ESM 的独立变更仍进入同一个更新队列。后续真实发行 smoke 又证明同次发布的包通知可晚于 wrapper 接纳，重复驱逐同一 namespace。公开 `watchChange` gate 在旧 dist 稳定复现报告序号多增一次；既有依赖观察范围内的已加载、字节相同通知现在去重，失败恢复与来源校验仍保留原流程，回归同时检查序号、实例和关闭。
4. **生产 conditions 不代表 Vite 会观察依赖。** 锁定版本仍默认忽略 node_modules。生产附件只观察实际已求值的普通 ESM 文件，补齐 Vite watcher 的遗漏；不全量扫描安装树，不改 CJS/native/singleton 热替换边界。
5. **Vite 配置默认打包会复制 token。** 生产使用 Node 24 的 native config loader；业务模块仍由 runner 编译和失效。独立配置不先 import 应用/插件，避免临时 bundled config 产生第二份领域身份。
6. **inline root 会掩盖文件配置中的冲突。** 真实拒绝测试发现必须在 config hook 合并前核对原始 root，再在 configResolved 核对最终 root；执行入口固定绝对 root，不使用进程级 chdir。
7. **解析过不等于加载过。** `import.meta.resolve()` 可以只定位未使用文件。native 使用 load hook 记录实际加载模块，再读取已加载的导出；不为归属判断预加载整个解析图。未使用且会抛错的模块作为负向回归。
8. **Node ESM 缓存不能重新解释共享绑定。** 同一文件的共享绑定事实在关闭后仍保留，hook、watcher 和 scope 会释放；冲突绑定即使在顺序 Host 启动也拒绝。新 native 部署输入由全新进程接纳。
9. **modules 复用目录签名需要准确 producer。** 原提案禁止冒用 native frozen artifact set。实际 distribution walker/DSSE 只证明清单列出的文件，复用它比另建签名协议更清楚：新增闭合 `modules-application` producer，部署清单显式 `runtimeClosure: packages`，不写 frozen deployment。搬移、只读运行后的 Ed25519 验证通过；外部依赖安装与可变来源不在其签名范围，见[发行边界](../DISTRIBUTION.md#动态来源的证明范围)。
10. **Node hook 不能证明任意旧 ESM 闭包。** 独立复核的真实 Node 反例先加载普通依赖、再加载 fresh application entry：旧 namespace 内捕获的 foreign token 不再经过 load hook。Node 的 resolve context 又不能区分 import 与 `import.meta.resolve()`，没有公开 ESM cache 查询。因此 native 的前置条件是全新进程 launcher 在业务闭包首次求值前调用；示例延后服务运行 imports。可靠拒绝范围是预加载 entry 和受控 cache 的绑定冲突，不声称证明任意历史依赖。不开反射、cache bust、强制预加载未使用文件或第二个执行器来伪装校验成功；定位但未加载的 URL 在 scope 结束时释放绑定。
11. **工作区可解析不等于独立应用拥有依赖。** 独立 tarball smoke 暴露共享 TypeBox 包只经间接依赖可达。共享选择以 startup.root 为安装权威，官方应用同步声明清单所使用的直接依赖，不通过 hoist、fallback resolver 或静默改选另一份安装掩盖缺项。实际安装 manifest 的 dependency/optional/peer 表也必须是范围映射；真实反例中数组表曾被当作未声明，optional 范围曾被忽略。现有事实 reader 校验所消费的映射，peer 保持 SDK 契约优先，optional 按安装语义覆盖同名 dependency；不修复或替换错误 manifest。
12. **Vite 返回关闭成功不证明 Host 已成功清理。** 真实 Node 回归证明 Vite 会吞掉 `closeBundle` 的 rejection。生产会话显式等待既有 Host owner，再执行插件和 Vite 清理，后续资源释放不被前一错误跳过，聚合错误和重复关闭保留真实结果。Native、Vite、HTTP listener 与生成 launcher 的启动失败若同时遇到清理失败，聚合保留两者，每层以原启动错误为 `cause`，不让清理错误替换诊断根因。真实端口占用回归检查内层 listener，而非只验证最外层聚合。附件 candidate 的异步 commit/rollback 同样不能假报接纳：类型要求同步 `undefined`，运行时校验返回值；已产生的异步工作交给原 Host effects 监督并排空。
13. **等待语法错误报告后立即修复会暴露观察丢失。** 原来固定等待掩盖了 Chokidar 的短时间 change 节流；更严格的真实 Package Manager/Vite 回归在已观察到拒绝后立即修复，仍停在旧失败报告。`awaitWriteFinish` 虽能合并写入，但 fresh Node 的公开 async_hooks 证明其内部 stat 轮询在 close 后仍可持续。私有 watcher 策略必须同时验证快速修复和关闭，不靠延长 sleep 或第二个更新协调器使测试通过。
14. **来源符号链接准入必须一致。** 独立 IO 反例发现 Native 会加载符号链接叶子，Vite 却会静默忽略。两者复用 Host 内部 discovery，拒绝声明根及 include 命中的符号链接入口，附稳定 `PLUGIN_SOURCE_SYMLINK` 和文件位置；父目录别名固定 canonical path，观察覆盖事实传给既有 evaluator。Chokidar 还会缓存坏叶子的 basename，阻止普通文件修复继续被观察；实现排除 SDK 对坏链接的跟踪，raw 仅触发同一 discovery 校验，标准事件负责普通入口接纳。每次 `entries()` 消费再次校验，避免独立工厂重评把仍然错误的来源误报为空 catalog 成功。纯声明仍无 IO，修复和关闭沿原更新队列验证。
15. **校验过的可变 options 不能在异步阶段换入口。** 实际调用流程中，Vite async config 与 tsdown config hook 都晚于 owner 创建；原对象别名可以在期间更改 entry、root、devConsole 或 modules/standalone 选择。执行/构建入口在创建时捕获所属选项，领域数组复制；真实异步配置与 modules 构建回归在调用后修改输入，仍验证原入口和原交付产物。standalone residual selection 复用原验证器并拒绝错误分组，不把非法输入默认为空。
16. **缺失父目录后来成为别名仍会伪装空来源。** 最小真实 IO 样本在打开空 `managed/entries` 后把 `managed` 建为 symlink；fresh Native 能发现目标文件，原 Vite 会话和独立工厂重评却都成功返回空 catalog、没有错误。既有观察 owner 现在检查 materialized ancestor 是否仍对应打开时固定的 physical path，不符以 `PLUGIN_SOURCE_PATH_CHANGED` 和 `file` 拒绝。恢复原普通目录可继续接纳并观察后续写入；重新解析父目录别名需要新 Vite 会话，不由同声明的 Host replacement 暗中重绑。
17. **合法 subpath 不能被对象原型语义吞掉。** 实际配置反例中 `./__proto__` 通过公开 export 校验，普通对象的 setter 却丢弃构建入口，输出清单继续声称该文件存在。入口收集改用 `Map`，再显式生成 own data properties；既有 modules 真实构建样本覆盖发行清单、Native 与 Vite 加载这一入口，不通过禁止合法包名或放宽清单验证规避问题。
18. **成员包拥有 CLI 不代表它拥有 workspace 输入。** 独立 tarball 生成项目在根目录完成 setup 和 verify，开发启动却在 `host/` 的 CLI 声明处停步，将该成员目录传给 doctor，因缺少 workspace 状态而拒绝。Host-vite 的原父链发现现在分别固定 doctor root 与 CLI 安装 owner，保持既有 Git/workspace/lockfile 边界；显式子根继续作为权威，错误安装与配置不借父目录掩盖。YAML、资源和成员验证仍由原 CLI doctor 拥有，见[开发资源接入](../CLI_WORKSPACES.md#开发资源接入)。
19. **Native 成功的 namespace 不需要为每个入口重新处理。** 真实 8/32/64 来源样本发现原循环反复读取已经校验的 owner manifest，64 个入口产生 2273 次 manifest 读取。loader 现在只处理待接纳的实际加载 URL，成功后移出 pending；缺失 owner、ABI 或物理归属失败不会标记成功。相同样本降到 193 次读取，不保留跨加载的 manifest 缓存。真实应用工厂中延迟加载的来源仍须接纳，第二个物理 owner 即使导出已验证 constructor 也必须拒绝。
20. **累计闭包不能靠反复复制前缀保存。** 上述 IO 修正仍留下反复遍历和存储累计 closure 的平方成本。每个 loader 改为一份唯一 URL 序列，成功入口保存自己的只读长度；恢复严格按该长度读取，关闭时冻结序列并释放 scope 资源。64 个入口加应用工厂的样本由 2145 个前缀 URL 引用变为 65 个唯一 URL，namespace 处理 65 次；cached application 的前缀不会被后加载来源扩大。这是加载事实索引，不是第二套模块图或 cache bust。
21. **Chokidar 的首次 add 不能逐个重新扫描目录。** 真实 8/32/64 入口样本中，初次打开每个 add 都执行完整 discovery，64 个入口触发 68 次 readdir 和 4352 次叶子 lstat。现在在 SDK readiness 前收集原事件，在同一处理队列中完整校验结束的观察 epoch，之后才返回会话；同样样本为 3 次 readdir 和 192 次叶子 lstat。live 事件和每次 entries 消费仍完整校验；初次枚举后的 symlink 注入仍保留原错误及文件位置，失败和 abort 都排空句柄。
22. **包名 namespace 不等于框架身份。** Chatbot 的实际 Hoshino 产物依赖相邻 binding 文件，standalone 内联其 JS 会破坏布局；旧构建校验又把任何 `@pluxel/*` residual 一律视作框架遗漏。调用方现在直接声明该原生依赖并选择实际 tracing，搬移后保留完整安装布局。框架校验只对实际 trace ledger 放行独立包；Core/Host 仍必须内联，显式选择或间接 trace 带入第二份均拒绝。真实回归搬移输出并删除整个来源及 node_modules 后仍可运行，不改包名、加 alias 或复制原生 loader。
23. **只改依赖声明不足以迁移真实下游。** Backend 的生产复制还读取已删除的 `pluxel.source-lock.json`，现改用 CLI 完成的 Git source setup 和实际 source HEAD 校验既有 build provenance。Rhythm 还消费旧 KOOK flat error；现在保留官方 `KookApiFailure` 和原 cause，以稳定 reason 和实际 membership 决定恢复，不根据错误字符串或模糊的 forbidden/not-found 删除绑定。四个 local-projects 与官方参考 Host 按各自固定 catalog 或来源需求选择 delivery，没有通用旧形状 wrapper。
24. **地址变化必须离线转换已有本地数据。** Rhythm 的实际 persistence 含旧 Kook owner 和 autoStart 各一条；旧 Discord 引用为零，当前 Vault v2 的 namespace、KV 和 blob 均为空。在确认没有该应用的在线实例后，单次维护复用原地址 parser、Config/Host state 校验、SuperJSON 和 Persistence 原子写入，先做完整备份及临时副本演练，再只转换两条地址。18 条配置、20 条 autoStart、非地址值和 Vault 字节保持不变；碰撞、解析失败、第二写失败回滚及聚合 cause 均验证。维护代码不进入仓库或启动流程，历史备份按原样保留。
25. **官方演示的冷编译期限属于应用策略。** 实际开发控制台发现 18 个启用插件的首次 Node 制品编译超过 Core 默认 1500ms。参考应用显式声明 30 秒启动期限，三种启动路径复用；原默认值和断言不变。同一 Vite 实例重新接纳后，18 个插件运行且无 issue，showcase 与 Workbench HTTP 均成功。导航检查使用真实 HTTP headers，避免 Node fetch 自动设置 cors 把正常导航误报为拒绝。

26. **服务包被内联不代表其所有 Plugin 都被选择。** Rhythm 的实际发行 catalog 没有 VaultAdmin，但旧 package-root assembly 仍复制 Services 的 VaultAdmin Workbench，产生第 12 个 producer。standalone 现在复用已验证静态 catalog 的 constructor binding 和现有语义收集器的源码/lowering ABI 事实，取得准确 canonical definition；相同选择同时约束源码 UI/Content 编译与包 inventory 组装，不执行工厂、不依据运行时类名或最终 chunk 文本猜测。未选择 renderer/Markdown 在读取前过滤；完整 inventory 仍先严格解析，所选树保留原摘要、冲突与复制校验。实际同模块双 Plugin 回归令未选 renderer/Markdown 不存在，仍只交付所选制品；Rhythm 原 11 producer 断言通过，发行清单从 629 降到 599 条。package/modules 构建继续编译各包的公开制品。
27. **所选快照不能清掉未读取领域的失效。** 新选择回归发现，B 已失效时先编译 A，旧全局 dirty 清理会让之后选择 B 使用旧导入事实。原 Workbench snapshot 现在只在成功提交实际读取 module 时清理其失效，保留单个有界快照及明确选择身份。回归覆盖全选、A/B 切换、空选择、坏导出拒绝和原输入修复；临时恢复旧全局清理的 mutation 稳定产生旧 digest，修正实现通过，没有另建 cache 或更新队列。
28. **源码解析成功不代表 Node 能消费原生依赖的 subpath。** Omni 搬离工作区的真实 Node 启动发现 `@node-rs/jieba/dict` 无 exports 且没有同名文件，因而在业务启动前拒绝。已安装 2.0.3 包拥有 `dict.js`；调用方直接导入该实际文件，保留第三方 loader。新增 fresh Node 分词回归覆盖真实字典和中英文计数；最终发行在缺少既有 TigerBeetle 输入时按原契约自然退出 1，运行前后清单完整，不以该负向结果宣称外部服务正向验收。
29. **相同构建默认值不构成独立预设契约。** 后续复核发现 `buildPreset()` 仅转发 `pluxel()` 并重复已有 Workbench 默认值。应用构建统一直接使用 `@pluxel/rolldown` 的原入口；Services 的源码、source/publish exports 与构建条目全部删除该包装，官方 Host、Create 模板、站点示例和四个本地项目同步迁移。`servicesPreset()`、`vitePreset()` 仍分别承担服务组合与开发附件；`standalone`/`modules` 是同一构建入口的交付选择，用法和边界只由[应用构建](../APPLICATION_BUILD.md)与[Host 配置](../../docs/host/configuration.md#生产构建)维护。

这些修正复用现有领域实现，没有新增 Executor/Backend registry、通用事务模板或第二个协调器。
