# 多来源目录生产

状态：设计草案；人工收录与通知回执已实现，自动 provenance 收录仍待验证，见 [Worker 项目](../../../projects/plugin-market/README.md)。上级：[提案总览](README.md)。
数据位置与配置更新由[底层结构](foundation.md)维护；本页拥有 CI 通知、扫描发现到目录提交的路径。

## 输入与发现

部署方配置获准来源和凭据，运营记录可登记这些来源下的包。
CI 发布通知是推荐的更新入口，定期扫描负责补漏与复核；市场客户端与安装器消费发行事实，不负责扫描。

候选可以来自 CI 的精确发行通知、完整包名登记、来源支持的关键词检索，以及已知包复核。
名称前缀与 `keywords: ["pluxel-plugin"]` 只是发现线索；不能证明制品有效。
不假设所有 npm 兼容 registry 支持搜索、全量枚举或同一变更流；不支持搜索时仍可从登记包开始。
搜索结果减少不能证明包已删除。npm 端点依据见 [Registry API](https://github.com/npm/registry/blob/main/docs/REGISTRY-API.md)。

## CI 发布通知与 npm provenance

插件发布管线在 npm 发布成功后，显式通知市场 registry、包名和精确版本。
通知只是待处理发行的定位信息；市场从获准 registry 读取版本元数据、下载实际 tarball，并取得该发行的 npm provenance。
包字节、摘要和来源关联以这次获取与验证为准，不接收 CI 上传的包作为替代，也不依赖通知中的仓库 URL。

来源证明复用 [npm provenance](https://docs.npmjs.com/generating-provenance-statements/)：验证原生证明并核对其绑定的包名、版本和 tarball 摘要，取得关联仓库、commit 与构建信息。
GitHub Actions、GitLab CI/CD 按 npm 支持的发布方式接入；满足条件的 [trusted publishing](https://docs.npmjs.com/trusted-publishers/) 自动生成 provenance，也可按 npm 文档显式启用。
其他平台沿用 npm 的实际支持范围，市场不另建 OIDC 发布者体系、证明格式或源码公开程度分级。

原生验证所需的 Sigstore 信任材料由市场部署与维护流程拥有，复用上游 TUF bootstrap 和更新机制；不能信任通知请求提供的证书根，也不能仅下载一份未经验证的 JSON 就替代信任链。
Worker 接入须通过真实正负例后才能启用自动收录；当前锁定组合的验证阻塞与信任根刷新待办见[可行性实验](../../spikes/plugin-market-worker/README.md#provenance-阻塞与最小复现)。

通知者只是提供发现线索，不必证明自己拥有该 npm 包。公开市场对获准的公共 registry 接受匿名通知，CI 无需另存市场发布密钥；私有来源的通知仍须有对应访问权限。
通知不能增加 registry、指定任意下载地址或修改展示记录。接收端限制输入、来源与发行的待办数量及重复频率；取得并验证 npm 制品后才决定能否收录，不把请求者身份当成发布者身份。

处理流程为：

1. Worker 校验来源与发行坐标，持久化通知待办后返回回执；此时只表示已接收。
2. 任务从 registry 拉包，验证 npm provenance 和下文的插件制品契约。
3. 校验通过后提交目录，记录原生 provenance 引用、验证结果及关联仓库信息，回执才报告已收录。

同一来源、包名和版本的重复通知复用待办，或复用已满足本次校验要求的完成结果；与已有发行字节冲突仍按下文拒绝。
接收响应丢失时，CI 可重复提交相同坐标取得回执，再查询处理结果。
扫描已收录但尚未取得 provenance 的发行，不能直接使后来的 CI 通知成功；仍需补齐同一制品的原生证明校验，无需重复创建发行。
版本或证明暂不可读时保留待处理状态，按有界重试策略处理；证明缺失或无效时明确报告，不能改信 `package.json.repository` 使本条通知路径成功。
失败重试保留前次结果并产生可追踪的后续尝试；重复通知不能无限重置重试预算。通知失败可单独重试，不撤销或重复执行已成功的 npm 发布。具体接口与回执字段在代表路径验证后确定。

人工登记与扫描继续服务私有及未提供 npm provenance 的来源；能够取得证明时复用同一验证逻辑，证明无效不能降级为无证明处理。
仓库展示由[目录消费](index-protocol.md#仓库与构建信息)维护；原生 provenance 不进入作者的静态 Plugin manifest。

## 一条生产路径

```text
读取来源配置、必要的运营记录、通知待办和扫描进度
  → 处理通知指定的发行，或发现/刷新一批候选
  → 从 registry 拉取精确版本，校验制品与可用的 npm provenance
  → 准备观测和发行记录；必要时写外部对象
  → 在有界事务中提交目录、查询索引与完成进度
  → API 读取已提交事实
```

候选与已验证发行记录分开。读取市场 API 不临时触发 npm 扫描，也不把尚未验证的新包伪装成可安装发行。
通知与扫描共用拉取、验证及提交逻辑。首版由 Worker Scheduled Handler 优先处理通知待办，再进行补漏与复核，通过 Drizzle 提交变化。
每次有包数、字节、并发和时间预算；保存已完成进度，后续触发继续处理。首版一个调度所有者即可，通知接收不承诺同步上架。
任务领取与完成提交使用数据库条件写入；重复或重叠触发不能同时提交同一任务。领取有期限，恢复后旧处理者的提交必须被拒绝，不能依赖 Worker 内存锁。
通知与复核各保留有界处理预算，持续通知不能使已知包的复核长期停滞。

## 增量与校验

已知包可利用来源支持的 ETag/Last-Modified 和已知版本摘要，避免反复下载未变信息。
扫描本身仍需发现变化；选择 SQL 并不会让不支持增量枚举的 registry 自动提供变更流。

进入可发布目录前，应绑定精确的 registry、包名、版本和制品摘要，按[发布格式](package-format.md)检查实际 tarball：
包内 manifest、公开入口、依赖元数据与资源必须一致。目录不能只相信 registry 的介绍字段。
下载与解包限制压缩字节、展开字节、文件数和路径，扫描不执行包脚本或 import 插件。
单个制品超过可处理预算时明确报告限制并结束本次尝试，不能在每次调度中从头重复耗尽预算、阻塞其他包。
同一来源同名同版出现不同字节时报告冲突，不静默替换。

观测保留时间和来源。不可变发行记录保存可以固定到字节的事实；人工规则和动态 tag 不混入制品摘要。
`dist-tags` 与弃用状态随 registry 观测更新；精确版本通知不覆盖后续 tag 调整，仍由复核补齐。版本选择保留 registry 的 tag 含义，不把最高 semver 自动当成 `latest`。
相同制品可复用验证结果，认证和可见性仍按来源处理。
真实 tarball 校验在 Worker 上的内存/CPU 预算属于[分阶段验证](delivery-plan.md#分阶段验证)。

## 版本覆盖与来源可用性

包被发现或已有一个已验证版本，不代表全部历史版本都已收录。优先处理通知指定的精确版本、当前 tag 指向和有界的历史补录；不能为展示一个包先下载其全部历史制品。
来源已知版本、待校验候选和已验证发行分别保存。目录查询只读已提交状态；需要补录时通过通知或管理刷新显式提交工作，普通 `GET` 不启动扫描。

例如 `latest` 已指向 `2.0.0`，而该版本尚未验证或校验失败：保留 tag 的真实指向与处理状态，已验证的 `1.9.0` 仍可选，但不能将它重新标成 `latest`。
版本覆盖与可选状态由[读取协议](index-protocol.md#版本选择与新鲜度)表达；市场收录和目标 Host 兼容是不同检查。

来源超时表示本次未能更新观测，不能证明包已撤回。确切观察到版本被移除或不可获取时，更新可用性与观测时间，保留既有发行摘要及验证历史。
上游撤回不改写已安装 Host 的运行状态；后续获取失败如实返回，不改用同名其他来源或其他版本。

## 提交与恢复

按[增量提交边界](foundation.md#目录如何增量提交)更新目录；Drizzle 条件更新与原子批次应同时约束关联写入，一次失败不能让读者看见半套包记录。
不同包可以逐批提交，无需等待整个 registry 扫描结束或替换全库快照。

| 情况                       | 结果                                           |
| -------------------------- | ---------------------------------------------- |
| registry 超时或认证失败    | 记录来源失败，保留已知事实；不当成全库删除     |
| 新制品校验失败             | 不公开候选，保存可定位诊断                     |
| 通知中的版本或证明暂不可读 | 保留待办并有界重试，不回报已收录               |
| 扫描中运营记录被编辑       | 扫描不能覆盖人工记录，读取使用已提交的运营事实 |
| 外部对象写完但事务未提交   | 旧记录继续服务，未引用对象可后续清理           |
| 任务重复或过期结果到达     | 相同事实可重用；过期观测不能覆盖较新事实       |
| 任务预算耗尽               | 保存已提交进度，报告未完成范围                 |

扫描状态不作为公开访问协议，凭据不进入产物。公开市场不能因扫描器有访问权限而公开私有数据。
API 返回新响应不意味着每个来源刚刚刷新；需要获取新事实的运营修改或发行通知，必须等待相应拉取与验证完成。
