# 市场运行与恢复的剩余设计

状态：数据底座已实现；本页保留恢复、持续扫描和目标部署的未决问题。上级：[提案总览](README.md)。

现有 Drizzle/SQLite schema、D1 接入、Wrangler 迁移、来源权限、人工条件编辑与通知保留边界见 [Worker 项目](../../../projects/plugin-market/README.md)。对应实现位于 `projects/plugin-market/src/schema.ts`、`store.ts`、`sources.ts` 和 `migrations/`。这些实现与当前 HTTP 参数均由正式项目文档维护。

## 保留与恢复

市场数据库保存人工运营记录、管理操作结果和已确认的发行摘要；其中一部分无法从 registry 重扫还原。查询索引与 HTTP 缓存可以从已提交记录重建。

部署方案还需要确定备份、保留期和恢复步骤。如果以后采用 R2，同时覆盖数据库引用的对象，并让对象清理保留足够的恢复窗口。
恢复流程需要满足：

- 保留同一来源、名称和版本的已确认摘要，避免清理或回退后接受不同字节作为同一发行。
- 在暂停写入与调度的维护窗口恢复；重新开放前，使恢复前的编辑版本和任务租约失效。
- 明确恢复到的时间与操作范围。较新的已确认操作若无法查证，返回无法确认，不自动重放。
- 回执过期和恢复丢失分别表达；普通进程重建后的 D1 回执可读不等于备份恢复已验证。

需要通过人工编辑、待办任务、发行记录和查询重建的完整恢复演练确定实现方案。恢复版本如何避免与旧客户端条件重合，是下一步必须解决的问题。

## 目录如何增量提交

现有人工刷新会原子保存发行、观测与审计。未来自动验证和扫描还需要把有效任务租约、目录写入和完成进度放在同一条件提交中；不能先完成租约检查，再无条件发布校验结果。

网络读取与制品校验在事务外完成；每次只提交有界包更新。扫描记录所用输入版本与观测时间，过期结果不能覆盖较新观测或人工编辑。整轮扫描无需一个大事务。

如果引入对象存储，应先完成对象写入与校验，再提交数据库引用。提交失败时旧目录继续可读，未引用对象按恢复保留期清理。当前产品没有 R2 依赖，是否需要它由实际对象大小决定。

## Cloudflare 运行边界

现有 Scheduled Handler 处理有界通知和回执清理；自动发现、tag 复核和 GitHub 刷新尚未由它调度。新增扫描应复用同一任务所有者，并为通知与复核分别保留预算，避免持续通知使复核停滞。

目标 D1 的并发、数据库容量、执行计划和 Worker CPU/内存预算仍需测量。现有本地 workerd/D1 测试和 tarball 上限是验证起点。只有观察到现有调度无法满足预算时，才考虑队列等额外平台能力。

## 验收条件

1. 在目标环境应用已有迁移，并验证代表容量下的查询、写入与批次时长。
2. 连续两轮扫描复用未变观测，预算耗尽后从持久进度继续；查询和人工管理始终可用。
3. 恢复包含人工编辑、发行和待办的备份，重建查询索引，并拒绝恢复前的编辑条件和租约提交。

迁移应用步骤由 [Worker 项目](../../../projects/plugin-market/README.md#制品容量与迁移)维护；自动生产设计见[目录生产](index-production.md)。
