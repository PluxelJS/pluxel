# 当前决定与验证顺序

状态：设计草案，尚未实现。上级：[提案总览](README.md)。
本页区分已选技术方向与仍待验证的契约，当前交付是设计文档。

## 已选方向

| 决定                                    | 目的                                              |
| --------------------------------------- | ------------------------------------------------- |
| Drizzle ORM + SQLite                    | 用同一 schema 与查询模型组织持久化，后续接入 D1   |
| Cloudflare Workers 及其生态             | HTTP 管理/查询、Cron 扫描、D1 持久化，R2 按需使用 |
| JSON 编辑/API，数据库按记录保存         | Agent 可定点修改，目录与规则可增量维护            |
| 带版本的条件更新                        | 防止并发修改丢失                                  |
| 人工记录、扫描状态、发行事实分开        | 保留意图与外部观测各自的所有者                    |
| Drizzle Kit 生成 SQL，Wrangler 应用迁移 | 保持 schema 变更可审查，D1 迁移历史有单一所有者   |
| 消费端 Market Plugin 配置远端 API       | 服务项目与长驻 Host，界面可选                     |
| 全新分发契约                            | 独立于 legacy schema、目录和 Package Manager      |

具体边界由[底层结构](foundation.md)、[目录生产](index-production.md)和[目录消费](index-protocol.md)维护。
当前围绕 Cloudflare 一条部署路线设计，不开展其他调度平台或数据库文件同步方案。

## 实施前验证

后续从 Drizzle SQLite schema、迁移和最小数据访问开始，再通过 Wrangler 的本地 D1 绑定验证 Worker 路径，最后验证目标 D1。
代表链路从公共和私有 registry 各读取一个真实插件制品，增量提交目录，经 Worker 查询并取得发行记录。
本地数据库用于验证同一数据模型，不作为另一套市场部署产品。

这条路径需要回答：

1. 生成的 manifest 能否从真实声明和打包内容获得，哪些要求需要作者明确补充？
2. Drizzle 生成的迁移能否在空库与已有库顺序应用，SQLite 与目标 D1 的约束、查询结果是否一致？
3. 条件更新未命中、批次 SQL 失败和过期任务到达时，关联记录与进度是否保持正确？
4. Worker 能否在实际 CPU、内存和触发时长预算内校验代表 tarball，批次耗尽后能否继续？
5. 目录变大后能否按索引分页；名称、scope 与中文描述的检索质量是否符合需求？
6. Agent 能否只修改目标记录；已有目录的运营修改是否无需重扫，新包登记是否明确等待扫描？
7. 私有凭据、私有观测和公开结果是否保持各自可见范围？
8. 第二次扫描是否复用未变事实；扫描停止后，HTTP 查询和运营管理是否继续可用？

表结构、具体 Drizzle/工具版本、查询索引、缓存 TTL、页大小和批次预算在上述验证后冻结。
同时观察数据库容量、实际读取/写入量与批次时长；不从“ORM 查询只返回十条”推断执行计划一定高效。
涉及 D1 driver 或迁移工具的能力以锁定版本实测为准，不仅凭 SQLite 单元测试宣布已经兼容。

## 交付顺序

| 阶段                   | 交付与完成条件                                                       |
| ---------------------- | -------------------------------------------------------------------- |
| 底座评审               | Drizzle/SQLite 与 Worker/D1 目标明确，数据和迁移所有者清晰           |
| 数据与 Worker 最小链路 | schema、迁移、条件编辑、增量扫描提交、按需查询；观察失败与第二次运行 |
| 发布与安装标准         | 冻结 manifest 与来源记录；同一制品在干净项目与真实 Host 消费         |
| 市场客户端             | 可配置 API、分页详情、实际安装回执                                   |
| 按需求补运营 feature   | 再设计 ban、重定向、规则冲突及安装检查等语义                         |

每阶段只将验证过的事实迁入正式工程和用户文档，不把提案示例当作已支持 API。
后续安装验证应覆盖公共/私有来源、共享 provider 和同名不同字节；当前不展开完整验收矩阵。

## 本次文档验证范围

核对当前 Core/Host 边界，以及 npm、HTTP、Drizzle 与 Cloudflare 官方依据；检查提案一致性、链接、Markdown 格式和 JSON 示例。
当前未安装依赖或运行数据库、扫描、Worker、安装与部署实验；性能、迁移、数据库适配和恢复行为均待实施验证。
