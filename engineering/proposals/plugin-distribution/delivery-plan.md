# 当前决定与验证顺序

状态：初版实施中；支持范围由 [Worker 项目](../../../projects/plugin-market/README.md)与[插件用法](../../../docs/plugins/package-manager.md)维护。上级：[提案总览](README.md)。
本页区分已选技术方向、实验依据与仍待验证的产品契约。

## 已选方向

| 决定                                         | 目的                                              |
| -------------------------------------------- | ------------------------------------------------- |
| Drizzle ORM + SQLite                         | 同一 schema 与查询模型，直接验证本地与目标 D1     |
| Cloudflare Workers 及其生态                  | HTTP 管理/查询、Cron 扫描、D1 持久化，R2 按需使用 |
| CI 发布通知，扫描补漏与复核                  | 从 registry 拉取精确发行，共用验证与提交路径      |
| 复用 npm provenance                          | 校验制品来源关联，展示仓库与构建链接              |
| 对外标准 HTTP，管理使用 Cap’n Web HTTP batch | 公开客户端直接接入，Agent 与后台共用管理契约      |
| 最小后台与按记录编辑                         | 包与发行、运营记录、任务诊断三个操作区域          |
| version / build / pack / publish 分工        | 版本工具、语义构建和原生包管理器各守权威输入      |
| tag、版本校验与来源可用性分开                | 新版待验证或来源失败时仍准确表达已有事实          |
| 固定发行与 Host 实际影响预检                 | 升级覆盖同包定义、fork 和依赖，拒绝过期操作前提   |
| 卸载保留数据，旧制品按引用清理               | 包选择、运行状态和业务数据由各自所有者管理        |
| JSON 编辑/API，数据库按记录保存              | Agent 可定点修改，目录与规则可增量维护            |
| 带版本的条件更新                             | 防止并发修改丢失                                  |
| 人工记录、通知与扫描状态、发行事实分开       | 保留意图与外部观测各自的所有者                    |
| Drizzle Kit 生成 SQL，Wrangler 应用迁移      | 保持 schema 变更可审查，D1 迁移历史有单一所有者   |
| 同一 Package Manager 可选配置远端市场 API    | 无市场仍可直接安装；界面可选                      |
| 新市场契约，复用不可变安装机制               | 不沿用旧市场 schema，也不重建已经验证的 pnpm 路径 |

具体边界由[底层结构](foundation.md)、[目录生产](index-production.md)、[目录消费](index-protocol.md)、[管理 API](management.md)和[发布格式](package-format.md)维护。
当前围绕 Cloudflare 一条部署路线设计，不开展其他调度平台或数据库文件同步方案。

## 开始实施的范围

初版实现放在 `projects/plugin-market` 与 `plugins/package-manager`。先交付公共 npm 的人工收录、目录 HTTP、Cap’n Web 管理，以及消费端的可选市场和准备/确认安装。通知保留持久回执和明确的 provenance 验证门槛；不能因为先交付目录而把未验证通知写成已收录。
自动 provenance 收录、完整发布 manifest 与 Host 影响预检仍按下面阶段验证，不要求把所有运营规则一次实现。

[2026-11-05 可行性实验](../../spikes/plugin-market-worker/README.md)已经验证本地 D1 的通知去重、条件编辑、关联写入、租约与进程重建后的回执，以及真实 Cap’n Web HTTP batch。普通回归 8 项通过，类型检查、迁移及 Worker dry-run 打包通过。
真实 npm provenance 的 Node 对照通过，但当前 workerd 的省略摘要算法调用与 Node 行为不一致，导致原生 Sigstore 校验正例失败。这是自动收录路径的实施门槛，不能以“库可打包”代替运行验证；负例也必须等正例通过后再验证。

下一步按以下顺序收敛：

1. 保留最小兼容复现，解决 Worker 验证路径，并明确部署方怎样提供、刷新可信 Sigstore 材料；沿用上游原生机制。
2. 从一个真实插件的标准 build/pack 产物验证最小 manifest，固定它与 exports、依赖及摘要的关系，再连接收录路径。普通 npm provenance 样本不能替代 Plugin 制品样本。
3. 将已验证的通知、领取与提交机制移入正式服务边界，补齐输入/资源预算、认证、重试和可观测诊断，再接目录查询及最小后台。

安装生命周期、私有来源、多市场与运营 feature 各在对应阶段验证；不会因为实验完成就开放未验证的路径。实验表和 RPC 方法不提前冻结成正式契约。

## 分阶段验证

从 Drizzle SQLite schema、迁移和最小数据访问开始，直接通过 Wrangler 本地 D1 绑定与 workerd 验证运行路径，再验证目标 D1。
代表链路从公共和私有 registry 各读取一个真实插件制品，增量提交目录，经 Worker 查询并取得发行记录。
公共样本覆盖 CI 发布 npm provenance、通知市场、从 npm 拉包验证和展示关联仓库的完整路径；私有样本保留登记与扫描路径。
本地数据库用于验证同一数据模型，不作为另一套市场部署产品。

这条路径需要回答：

1. 生成的 manifest 能否从真实声明和打包内容获得，哪些要求需要作者明确补充？
2. Drizzle 生成的迁移能否在空库与已有库顺序应用，SQLite 与目标 D1 的约束、查询结果是否一致？
3. 条件更新未命中、批次 SQL 失败、重复领取和过期任务到达时，关联记录与进度是否保持正确？
4. Worker 能否在实际 CPU、内存和触发时长预算内校验代表 tarball，批次耗尽后能否继续？
5. 目录变大后能否按索引分页；名称、scope 与中文描述的检索质量是否符合需求？
6. Agent 与最小后台能否通过同一 Cap’n Web 管理契约只修改目标记录，明确报告校验与版本冲突；已有目录修改是否无需重扫？
7. 私有凭据、私有观测和公开结果是否保持各自可见范围？
8. 第二次扫描是否复用未变事实；扫描停止后，HTTP 查询和运营管理是否继续可用？
9. Worker 能否使用适配其运行环境的 npm provenance 验证实现，拒绝包名、版本、摘要或来源关联不符的证明，并返回实际仓库与构建链接？
10. 重复通知、版本或证明暂不可读、证明无效以及任务中断时，回执、重试和目录提交是否一致；通知重试是否无需重新发布 npm 包？
11. 公共 HTTP 的状态、分页、条件缓存和通知回执是否能用普通 HTTP 客户端消费，OpenAPI 是否与运行时校验一致？
12. Cap’n Web batch 的认证、参数校验、逐项结果和结束后的 stub 释放是否正确；响应丢失后能否重新核对记录或查询任务结果，避免盲目重放？
13. 版本计划、build 与原生 pack 能否生成可独立消费的依赖声明；缺失 peer、错误 optional、未转换协议或开发路径能否在发布前被定位？
14. 构建、验证、npm 发布与 provenance 是否指向同一 tarball；同批包部分发布失败、通知重试及后续 dist-tag 变化是否保持真实结果？

表结构、具体 Drizzle/工具版本、查询索引、缓存 TTL、页大小和批次预算在上述验证后冻结。
同时观察数据库容量、实际读取/写入量与批次时长；不从“ORM 查询只返回十条”推断执行计划一定高效。
涉及 D1 driver 或迁移工具的能力以锁定版本实测为准，不仅凭 SQLite 单元测试宣布已经兼容。

## 优先验证的失败场景

用少量可复现样本检验跨边界行为；不以每个组件单独成功替代完整链路。

| 场景                                                            | 必须观察到的结果                                                                              |
| --------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| npm 发布成功，市场响应丢失；重复匿名通知同一公共发行            | 按相同坐标取得回执并确认结果，复用待办与验证结果，不要求重新发布或另配发布者密钥              |
| 扫描已收录，provenance 稍后才可读；此前通知已失败               | 补验同一制品的证明，后续尝试可追踪，旧收录状态不冒充本次通知验证完成                          |
| `latest` 移到未通过校验的版本；registry 随后超时                | 保留真实 tag 指向、旧版选择与观测时间，失败不改写成旧版 `latest` 或空市场                     |
| 两个 registry 提供同名不同字节的包；目标包含多个 Plugin 与 fork | 来源选择明确，Host 身份冲突可见，升级影响覆盖整个包及相关节点，不能并存冒充独立实现           |
| 预检后另一操作改变选择；接纳时旧代停止而新代 init 失败          | 过期前提被拒绝；已进入接纳的失败按真实阶段报告，回执不声称原运行状态已恢复                    |
| 托管安装跳过脚本且缺少生成物；卸载或降级仍有旧制品引用          | 缺失事实明确失败；保留业务数据与仍被引用的制品，不承诺外部副作用回滚                          |
| 单个 tarball 超出预算；同时还有其他通知和已知包复核             | 大包有明确终止结果，其余工作继续推进，重复通知不能无限重置预算                                |
| 恢复数据库且已有 R2 对象或过期回执                              | 人工记录和发行引用可恢复，查询索引可重建，恢复前写入/租约不能误提交，无法确认的操作不自动重放 |

这些是实现验收要求，不是本轮已通过的测试。来源、版本和安装语义分别由[目录生产](index-production.md)、[读取协议](index-protocol.md)与[安装边界](installation.md)维护。

## 交付顺序

| 阶段                   | 交付与完成条件                                                                                     |
| ---------------------- | -------------------------------------------------------------------------------------------------- |
| 底座评审               | Drizzle/SQLite 与 Worker/D1 目标明确，数据和迁移所有者清晰                                         |
| Worker 可行性实验      | D1、条件提交和管理传输已有本地证据；原生 provenance 正例及篡改负例通过后才完成该路径验证           |
| 数据与 Worker 最小链路 | schema、迁移、条件编辑、通知待办、npm 拉包与 provenance 验证、增量提交和查询；观察失败与第二次运行 |
| 管理 API 与最小后台    | Cap’n Web 管理契约；Agent 与后台走同一编辑、冲突和回执流程                                         |
| 发布与安装标准         | 冻结 manifest 与来源记录；同一制品在干净项目与真实 Host 消费，验证升级影响与卸载边界               |
| 市场客户端             | 可配置 API、分页详情、provenance 仓库链接与实际安装回执                                            |
| 按需求补运营 feature   | 再设计 ban、重定向、规则冲突及安装检查等语义                                                       |

每阶段只将验证过的事实迁入正式工程和用户文档，不把提案示例当作已支持 API。
后续安装按上述代表场景验证公共/私有来源、共享 provider、同名不同字节以及 live/待重启两条路径，再冻结具体安装 API。

## 当前验证范围

核对当前 Core/Host、构建与发布边界，以及 npm、pnpm、HTTP、Cap’n Web、Drizzle 与 Cloudflare 官方依据；检查提案一致性、链接、Markdown 格式和 JSON 示例。
独立实验已执行的命令、版本、通过项与失败项以[实验记录](../../spikes/plugin-market-worker/README.md)为准；本地迁移与进程重建不证明目标 D1、备份恢复或生产资源预算。
初版已接入独立 Worker、人工 npm 收录和公共目录、Cap’n Web 管理，以及统一 Package Manager 的市场读取和准备/确认安装。当前验证命令与限制以所属项目和插件文档为准，不把实验结果当作这些实现的回归。
新的独立 Plugin manifest、自动 provenance 收录、扫描发现、私有来源、完整 Host 影响预检及远端部署仍待后续验证。当前没有关闭证明检查，也不会把仅接收到的通知回执标成已收录。
