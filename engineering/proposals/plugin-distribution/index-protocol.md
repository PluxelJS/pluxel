# 目录消费与缓存

状态：设计草案；当前 HTTP 路由与限制见 [Worker 项目](../../../projects/plugin-market/README.md)。上级：[提案总览](README.md)。
本页拥有对外 HTTP、目录读取与缓存语义；[底层结构](foundation.md)拥有存储与发布方式。路由和 schema 尚未冻结。

## 权威与按需访问

市场发布者的已发布目录与当前运营配置形成有效市场视图。
消费端连接明确的市场 API；扫描策略、来源发现与运营规则的解释留在生产/服务端。
包详情必须保留 registry、包名和发行来源，市场资源 ID 不替代 [Plugin identity](../../PLUGIN_IDENTITY.md)。

读取侧分成三种大小不同的资源：

| 资源           | 内容与读取时机                                                        |
| -------------- | --------------------------------------------------------------------- |
| 小入口         | 协议版本与读取入口；连接市场时读取，不要求携带全库快照                |
| 查询与包摘要   | 当前列表页、检索结果、按包详情、版本页；按操作读取                    |
| 不可变发行对象 | 精确来源、版本、tarball URL、integrity、manifest 引用；选中发行后读取 |

一个组织市场可收集多个 registry，消费者不需要一源一个市场。
包来源与凭据分开；产物中的 URL 不携带私有 token，访问凭据由应用部署方提供。

## 标准 HTTP 接口

对外读取与 CI 通知使用标准 HTTP + JSON，客户端可直接使用 `fetch` 或常规 HTTP 工具。管理写入由独立的 [Cap’n Web 管理入口](management.md)承担。

| 操作                             | HTTP 语义                                                           |
| -------------------------------- | ------------------------------------------------------------------- |
| 目录入口、查询、详情、版本和发行 | `GET`，成功返回 `200`；分页、筛选与排序使用显式查询参数             |
| 缓存重新验证                     | `ETag` / `If-None-Match`，表示未变时返回 `304`                      |
| CI 发行通知                      | `POST` JSON；新任务持久接收后返回 `202`、回执及 `Location` 查询地址 |
| 通知处理结果                     | `GET` 回执；请求成功与任务的待处理、已收录或失败状态分别表达        |

重复通知按[目录生产](index-production.md#ci-发布通知与-npm-provenance)复用任务；未完成返回 `202`，已完成返回 `200` 及已有结果，任务失败仍保留其领域结果。
非法输入、认证失败、资源不存在、冲突及限流使用对应 HTTP 状态；错误正文采用 [RFC 9457 Problem Details](https://www.rfc-editor.org/rfc/rfc9457.html)，以稳定 problem type 及必要的字段诊断供程序分支。
限流或暂时不可用时按适用情况提供 `Retry-After`。不把读取失败包装成空列表或 HTTP 成功；已成功读到的失败任务回执仍是正常查询结果。

公私有访问共用协议，在读取前确定认证主体与可见范围。公共发行的通知回执只返回可公开的坐标、处理状态与诊断；内部日志和管理操作记录不随回执公开。
私有通知及回执要求对应权限，不能借查询地址读取其他主体的任务或私有来源信息。
正式 API 提供 OpenAPI 描述与短调用示例；输入 schema、TypeScript 类型和文档来自同一契约，路由、字段与协议版本在代表路径验证后冻结。

## 仓库与构建信息

版本详情返回经[目录生产端](index-production.md#ci-发布通知与-npm-provenance)验证的 npm provenance 引用及其关联仓库、commit 和构建链接。
市场直接展示这些原生信息，仓库关联以验证结果为依据；`package.json.repository` 只保留作者声明的含义，不能替代验证结果。
没有 npm provenance 的发行不展示已验证的来源关联。
展示内容参考 [npm provenance 详情](https://docs.npmjs.com/viewing-package-provenance/)，具体响应字段随发行记录一并确定。

## 查询边界

数据访问以 Drizzle ORM 的 SQLite schema 与查询为基础，Worker 路径接入 D1，在数据库内完成筛选和分页；driver 与迁移职责见[底层结构](foundation.md#drizzle-与迁移职责)。
字段筛选与排序使用适当索引，关键词检索可以验证 D1/SQLite 提供的 [FTS5](https://developers.cloudflare.com/d1/sql-api/sql-statements/)；不自行在 R2 上建设倒排索引。
全文搜索能力不直接证明中文分词、包名或 scope 的检索效果，需用代表查询验证。不能把全表加载到 Worker 后再切出十条。

列表与版本历史分页，详情与 manifest 独立获取。分页使用稳定排序和明确的更新语义，不要求数据库保留每个历史视图；查询变化或游标无法继续时明确重新开始。
应用当前配置后再确定返回结果与下一页位置；不能先切一页再简单删项，造成遗漏或错误分页。
同一响应与缓存标识基于一致读取；目录提交与运营更新各自推进。

## 版本选择与新鲜度

包详情与版本页分别表达 registry 的 tag 指向、市场已验证的版本及候选处理状态；未补录的历史范围不能呈现成“这些版本不存在”。具体覆盖字段随分页契约确定。
`latest` 或其他 tag 指向尚不可选的版本时，返回其实际状态，不能静默换成较旧发行。用户可显式选择其他已验证版本。
一旦选择发行，安装请求固定 registry、包名、精确版本与摘要；刷新页面、tag 移动或重试均不改变已提交请求的版本选择。

相关结果携带来源最近成功观测时间及当前获取状态。API 刚返回 `200` 或 `304` 只说明目录读取结果，不证明刚刚连接过 npm。
已有发行事实与当前来源可用性分别展示：超时可保留旧事实，确认撤回也不删除历史验证记录；是否仍能取得包由实际获取结果决定。
包的整体收录状态不能替代每个版本的校验状态，provenance 仓库链接也以所选发行的验证结果为准。

## 缓存与更新

| 数据                               | 建议方式                                       |
| ---------------------------------- | ---------------------------------------------- |
| 当前入口、检索结果、包详情、版本页 | ETag / If-None-Match；公共读取可短期缓存       |
| 按内容摘要寻址的发行对象           | 公共对象长期缓存与 immutable；字节改变则换地址 |
| 运营配置管理读写                   | 经过认证，绕过公共缓存；更新使用条件写入       |
| 私有查询和对象                     | 默认私有条件缓存；认证主体隔离，不进入公共 CDN |

动态结果的 ETag 与实际响应及可见范围关联；目录或运营记录改变了结果后，不能继续将旧表示判为未修改。
短期缓存的具体 TTL 待测量决定；“无需重扫即可采用新配置”不等于既有缓存立即失效。
若将来某个操作需要强制读取最新规则，应在那个 feature 中明确一致性要求，不由浏览缓存承担。

HTTP 的条件请求、缓存重新验证与不可变缓存分别遵循 [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)、[RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html) 和 [RFC 8246](https://www.rfc-editor.org/rfc/rfc8246.html)。
数据库提交成功不等于 CDN 已刷新；缓存命中与读取数据库的语义分别表达。

## 发行事实与后续协议

发行记录绑定来源、精确版本、下载位置、字节摘要和静态 manifest。
客户端核对可信目录给出的摘要，再校验实际对象；同名同版或缓存命中都不能代替字节校验。
长期保留的发行对象只表达固定事实，当前展示或运营决定由有效市场视图表达。

安装器消费这些记录，同时完成自己的依赖解析与 Host 检查，见[安装边界](installation.md)。
ban、重定向、安装时是否在线检查、离线安装以及多市场规则冲突的具体语义后续单独设计；
本轮不冻结 admission 路由，也不要求每次安装依赖常驻准入服务。
