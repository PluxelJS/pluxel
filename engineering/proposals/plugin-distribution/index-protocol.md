# 目录协议的剩余设计

状态：HTTP 查询、通知、FTS5、分页和条件缓存已实现；本页保留后续协议问题。上级：[提案总览](README.md)。

当前路由、DTO、来源权限、缓存策略和查询参数由 [Worker 项目](../../../projects/plugin-market/README.md#http-契约)维护，代码入口为 `src/protocol.ts` 和 `src/worker.ts`。

## 标准 HTTP 接口

现有 HTTP + JSON 协议已供 Package Manager 和独立网页使用。对外稳定发布还需确定输入 schema、TypeScript 类型和 OpenAPI 描述的共同生产者，避免另维护一份手写协议。

管理写入继续使用[现有 Cap’n Web API](../../../projects/plugin-market/README.md#市场管理)。普通消费者的私有目录授权尚未实现，需与[客户端认证设计](market-client.md)共同确定主体、可见范围和凭据生命周期。

## 仓库与构建信息

当前目录展示作者声明的仓库链接和显式获取的 GitHub stars；这两项已有独立来源与观测时间。`verified` provenance 类型已有预留，实际生产路径仍被[原生验证门槛](index-production.md#ci-发布通知与-npm-provenance)阻塞。

自动验证完成后，所选发行应返回原生 provenance 引用、仓库、commit 与构建链接，并区分作者声明和验证结果。具体字段只从真实验证输出确定；没有证明的发行继续表达缺失状态。

## 版本选择与新鲜度

当前 tag 与已检查发行分别读取，`latest` 不因新版本未收录而回退；版本页已经表达 `indexed-only` 覆盖范围。后续需要明确：

- tag 指向未收录发行时，如何读取候选的待办、失败或尚未发现状态。
- 来源最近成功观测、当前暂不可达与确认撤回分别如何表达。
- 历史补录的已覆盖范围如何随扫描进度展示，避免未补录被解释为版本不存在。

这些状态来自[生产端观测](index-production.md#版本覆盖与来源可用性)，普通目录读取不启动扫描。安装仍固定用户所选的精确发行，不随 tag 改变或读取失败切换版本。

## 查询与缓存演进

现有 FTS5、查询绑定游标、SQL 内筛选及缓存 TTL 已有实现。后续按真实目录规模验证名称、scope、中文描述和标签查询质量，测量索引与分页执行成本，再决定是否需要调整。

新候选状态、来源可用性或消费者权限进入响应时，缓存标识必须反映它们。受保护结果按主体隔离；目前认证响应使用 `no-store`，更细的私有缓存需有明确需求与验证。

新 manifest 若形成独立可读取资源，再确定其地址、字节和缓存寿命。当前精确发行响应可受隐藏与来源权限影响，不能仅凭版本固定就改为永久公开缓存。

## 验收条件

使用普通 HTTP 客户端验证生成的 OpenAPI 与实际输入校验一致。代表样本应包含未收录的 `latest`、过期观测、确认撤回、不同主体可见范围，以及同一发行的声明仓库和已验证仓库信息。

ban、重定向、离线授权与多市场政策冲突尚无已选语义。目录隐藏只控制浏览可见性，是否影响安装或已运行插件需要独立需求与设计。
