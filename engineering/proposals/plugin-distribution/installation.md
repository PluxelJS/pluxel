# 安装与生效的边界

状态：设计草案；初版准备/确认安装流程见 [Package Manager 用法](../../../docs/plugins/package-manager.md)。上级：[提案总览](README.md)。
本页确定项目依赖和长驻 Host 共用的职责，以及升级、卸载必须保留的语义；完整 Host 影响预检和多来源安装仍待后续实现。

## 跨 registry 获取

安装编排接收市场返回的精确发行记录，不承担候选发现或扫描。
获取层仍需 registry 来源、包名、版本、tarball URL、integrity 和本地认证；“不绑定 registry”表示来源可变，而不是丢弃来源。
同一安装可以涉及公共与私有 registry，不要求先把所有包镜像到一个自定义 registry。

同名同版不能证明相同制品。市场选择、原生 registry 配置和实际获取结果冲突时要明确报告，不能默默换源。
凭据由部署方按目标绑定，不能通过市场返回任意 URL 就向其转发认证。

## 发行身份与 Host 身份

registry、包名和精确版本定位一个发行，摘要进一步固定其字节；Host 的 [Plugin identity](../../PLUGIN_IDENTITY.md)由公开入口与具名导出确定，registry、版本、摘要和安装路径不参与身份。
因此同名包换源或升级是在替换实现，不能通过换目录、加版本后缀或创建 fork，使同一公开身份的两个实现同时进入同一 Host catalog。
一个 catalog 中同一 npm 包名只有一个已选择的物理包来源；普通实现依赖仍可按原生包管理器规则保留多版本。

一次包升级可能同时改变多个 Plugin 导出。每个 definition 的 default 和所有 fork 共享实现，影响检查必须覆盖这些节点、被移除的导出和相关依赖，不能只看点击升级的那个实例。
应用固定 import 已拥有同名包时，应修改项目依赖及装配；托管安装报告来源冲突，不用第二份包覆盖应用声明。不同 Host 部署可以各自选择不同发行。

## 插件依赖与普通 npm 依赖

| 依赖                        | 职责                                                     |
| --------------------------- | -------------------------------------------------------- |
| Plugin 与 required provider | 使用静态声明确定插件关系，再核对来源、版本和目标 Host    |
| optional provider           | 按实际选择与可用能力参与，不因市场中存在就自动启用       |
| 宿主共享框架或服务          | 核对真实装配和模块身份；安装第二份包不能伪装满足共享要求 |
| 普通实现依赖                | 保留 npm 原生求解与锁定语义，不要求所有库都收录为插件    |

建议先选一个成熟获取/解析引擎，验证真实多来源依赖和 peer context，再确定安装 API。
只向命令传顶层 tarball URL 不能证明所有传递依赖来源正确；不能把所有 peer 都当成 Plugin。
来源、精确字节和原生依赖关系应保留在可追溯安装结果中，不手写另一套与包管理器竞争的通用锁格式。
原生依据见 [npm lockfile](https://docs.npmjs.com/cli/v11/configuring-npm/package-lock-json/) 与 [pacote](https://github.com/npm/pacote)。

托管安装首版以预编译制品为输入，默认不执行包及依赖的安装脚本；缺少必需生成物时报告实际校验或接纳失败，不把禁用脚本后的安装命令成功视为插件可运行。
支持哪些传递依赖来源、是否需要额外脚本策略及何时检查运营规则，随真实获取引擎验证后确定。
项目直接执行的原生包管理器命令可能已经运行脚本，之后的插件检查不能追溯性地保证此前没有执行代码。

## 两种消费方式

| 消费方式  | 安装结果                       | 生效所有者           |
| --------- | ------------------------------ | -------------------- |
| 项目依赖  | 项目依赖与锁文件变更           | 项目构建、装配与部署 |
| 长驻 Host | 独立托管环境中的制品与持久选择 | Host 接纳及其执行器  |

同一 tarball 和[发布格式](package-format.md)供两者消费，来源完整性与兼容事实保持相同。
项目安装应保留可审查变更；后续构建失败不意味着依赖变更从未发生。
Host 在线安装避免修改运行框架自身的依赖，保存制品与选择也不等于实际启用。

执行器支持 live 时可请求接纳；需要新进程时明确报告待重启。实际能力遵循[当前动态来源](../../../docs/host/configuration.md#动态来源)。
运行身份仍使用[公开入口与具名导出](../../PLUGIN_IDENTITY.md)，不能把版本路径或市场显示名变成 Plugin identity。

## 安装与升级的预检

安装能力先确定目标项目或 Host profile、精确发行和当前安装选择，再执行获取与依赖求解。选择 `latest` 只发生在形成请求时；任务重试继续使用同一版本和摘要。
长驻 Host 在制品写入或选择修改前检查已声明的动态来源及执行策略，缺少来源时直接报告；与[当前来源契约](../../../docs/host/configuration.md#动态来源)保持一致。

预检结果供界面与 Agent 读取，应说明实际影响：

- 包与共享 provider 的版本要求、来源冲突、缺少的宿主能力及无法满足的 peer。
- 会替换或移除的 Plugin definition、对应 default/fork，以及 Host/Core 判断需要处理的依赖节点。
- 安装选择和启用意图各自的变化、是否可 live 接纳或必须新进程生效。

静态 manifest 提供声明事实，Host/Core 提供实际节点、依赖和接纳结果；安装器不复制一套运行图，也不自动安装或启用 optional provider。
预检绑定它所依据的安装选择版本和 Host 状态。提交时按所属领域重新核对；并发升级或配置变化使影响失效时返回冲突并重新准备，不能默默扩大操作范围。
同一目标的选择更新由安装领域协调，实际接纳由 Host/Core 协调；计划通过不意味着可以绕过后者的最终检查。具体版本标识与提交接口在真实 Host 路径验证后确定。

## 运行与结果所有权

安装领域拥有获取、校验、制品保留和安装选择；Host/Core 拥有配置、启用意图、接纳和运行事实。
Market Plugin 只是入口，不通过界面状态制造运行成功。

准备失败、已保存但未应用、旧代已停止而新代启动失败，必须分别表达；生命周期依据见[现有语义](../../CORE_LIFECYCLE_SEMANTICS.md)。
脚本、初始化和外部数据写入不天然可回滚，安装不能宣称是跨文件、进程与外部服务的原子事务。
操作回执保留固定发行、保存结果、实际接纳结果及必要诊断；断线后查询原操作，不以重新发起一次安装来猜测是否成功。

## 卸载、降级与旧制品

包卸载覆盖包内全部 Plugin。需要停止的节点、required 依赖阻塞和 optional 变化由 Host/Core 按现有生命周期处理，不由安装器私自强停依赖或直接删除仍在运行的来源。
保存移除选择、撤回定义、节点停止与删除制品是不同阶段；只能在新进程生效的执行器报告待重启，不能提前宣称卸载完成。

卸载默认保留配置和业务数据。清空数据必须是数据所有者提供的独立操作；包被市场移除、上游撤回或卸载都不意味着可以删除数据库、文件或外部资源。
旧制品仅在不再被安装选择、进行中操作或执行器引用后清理；不能证明引用已释放时保留，避免删除尚在运行或待启动的实现。
回到旧版本仍是一次针对固定发行的安装与接纳；旧 tarball 可用不代表数据库迁移、初始化副作用或外部写入可回滚，不提供笼统的“一键恢复全部状态”承诺。

是否需要在线 admission、如何恢复已有部署以及 ban 的作用范围，留给后续明确需求。
市场底座只提供可按需获得、可校验、来源明确的发行事实，不预先把所有安装绑定到某个政策服务。
