# 市场管理 API 与最小后台

状态：设计草案；初版 Cap’n Web API 与管理脚本见 [Worker 项目](../../../projects/plugin-market/README.md)，后台页面尚未实现。上级：[提案总览](README.md)。
本页拥有市场管理协议、Agent 调用和后台界面的范围；数据与条件写入由[底层结构](foundation.md)维护。

## 协议按调用方分工

| 入口        | 协议与调用方                                        | 职责                                         |
| ----------- | --------------------------------------------------- | -------------------------------------------- |
| 目录读取    | 标准 HTTP + JSON；Market Plugin、CLI 与第三方客户端 | 查询、详情、版本、精确发行与 provenance 链接 |
| CI 发行通知 | 标准 HTTP + JSON；任意支持的 CI                     | 提交精确发行坐标、查询本次处理回执           |
| 市场管理    | Cap’n Web；后台、CLI 与 coding agent                | 运营记录、诊断、刷新及重试                   |

公开读取与通知遵循[HTTP 协议](index-protocol.md#标准-http-接口)。公开协议也可服务需要认证的私有市场，不等于匿名访问。
管理端不另维护一套同义 REST 写接口；两种协议调用所属领域的同一查询、校验与提交逻辑。
通知只有请求处理某个发行的能力，不授予运营记录编辑权限；npm provenance 仍只负责[发行来源验证](index-production.md#ci-发布通知与-npm-provenance)。

## Cap’n Web 接入

首版使用 Cap’n Web HTTP batch。Worker 通过原生 `newHttpBatchRpcResponse()` 接入，客户端使用 `newHttpBatchRpcSession()`，不封装另一套 RPC wire protocol。
它适合有限的管理请求和批量读取；一个 batch 完成后其 stub 失效，后续操作创建新 batch。参考 [Cap’n Web HTTP batch](https://github.com/cloudflare/capnweb/blob/main/packages/docs/src/content/docs/transports/http-batch.mdx)。

认证入口验证部署方提供的凭据后，返回绑定主体和权限范围的管理 target；每个 batch 独立建立授权，服务端校验参数与目标资源权限。
凭据不写入 URL 或日志。限制单次输入、批量条数和触发工作的数量；类型声明与 RPC 引用不能代替这些运行时检查。原生模式见 [Cap’n Web security](https://github.com/cloudflare/capnweb/blob/main/packages/docs/src/content/docs/guides/security.mdx)。

业务记录与任务回执保存在 D1；RPC target 只持有当次请求的身份和调用上下文。断线不删除任务，也不撤回已经提交的修改。
首版不需要订阅、持久 WebSocket 或 Durable Object；这是独立市场服务的选择，消费端 Workbench 保持[现有会话契约](../../WORKBENCH.md)。

## Agent 与界面共用的操作

管理契约先覆盖实际操作：

- 按来源、包名或记录标识分页查找，读取单条记录及其版本。
- 校验拟提交的 JSON，返回字段位置和诊断；按预期版本创建、更新或显式删除运营记录。
- 查看通知、扫描任务与失败详情，提交指定包的刷新或重试，读取持久回执。

导出可独立导入的 TypeScript 管理契约与输入 schema；它们不依赖 Worker binding、数据库连接或后台 UI。
CLI、Agent 和界面共用该契约及原生 Cap’n Web 客户端。每个操作说明输入、返回结果、完成阶段与可恢复失败，提供短小的 TypeScript 调用示例；不要求 Agent 操作浏览器或手写 wire JSON。
首版不增加 MCP 包装、远程任意代码执行或数据库管理接口。具体方法名、契约包位置和客户端版本约束在最小链路验证后确定。

## 写入、批量与重试

记录修改沿用[版本条件写入](foundation.md#agent-如何编辑运营配置)。预检用于发现问题，提交时再次校验；预检通过不保留写入权，也不保证版本仍有效。
版本冲突、输入错误与目标不存在返回可判别的领域结果，附必要的字段位置或当前版本；网络及 RPC 失败保留原生错误，调用方不解析 message 判断业务结果。
记录修改的响应丢失时重新读取记录与版本，核对当前状态；不能自动换成新版本重放旧编辑。

HTTP batch 只合并传输，不使其中多个写操作成为事务。首版编辑单条记录；批量操作有条数上限并逐项报告结果，同一记录的依赖修改显式串行。
若以后需要多记录原子修改，应设计一项明确的领域操作并验证 D1 提交边界，不能靠 `Promise.all()` 获得原子性。

刷新与重试返回持久回执，接受任务与完成任务分别报告。有副作用的任务提交使用一次生成、重试复用的请求标识；同一主体重复提交相同请求返回同一回执，复用标识但内容不同则拒绝。
任务提交响应丢失时先按原标识查询结果，不生成新标识盲目重做；回执保留期与到期后的查询结果在接口中明确。关闭界面或释放 stub 只结束客户端等待。
管理提交保存操作者、目标与结果所需的最小操作记录，凭据不进入记录。

## 契约与部署更新

管理契约和静态后台配套发布；CLI 与 Agent 使用明确支持的契约版本。调用契约版本、记录版本和插件 manifest 的 `formatVersion` 各自表达不同事实，不用一个版本号兼任。
破坏性管理契约变更必须在写入前拒绝不支持的旧客户端；旧页面保留编辑内容并提示刷新，不能忽略不认识的字段后提交。兼容部署不必改变契约版本，首版不维护多套管理写入协议。
公开 HTTP 的协议版本独立维护；后台页面升级不要求插件作者重新发布包。

## 后台界面从简

后台是独立市场服务的小型静态页面，复用同一管理 API；不要求安装完整 Pluxel Host 或 Workbench。
首版只提供三个操作区域：

| 区域       | 内容与操作                                                            |
| ---------- | --------------------------------------------------------------------- |
| 包与发行   | 搜索、来源、版本、provenance 仓库链接、最近处理结果；登记包和请求刷新 |
| 运营记录   | 列表、单条 JSON 编辑、校验与差异、按版本保存和显式删除                |
| 任务与诊断 | 通知/扫描进度、失败原因、回执与指定任务重试                           |

入口显示待处理和失败摘要，复用列表筛选，不另建统计仪表盘。JSON 编辑与 Agent 使用相同 schema，常用字段再按需求提供表单。
部署 binding、registry 凭据和 schema 迁移仍由部署工具管理；后台显示必要状态与凭据引用，不提供数据库控制台。
浏览器保存失败或版本冲突时保留当前编辑内容并显示差异；任务页面按需读取状态，页面关闭即停止读取。
保存结果、目录收录结果与公开缓存刷新分别展示，不用一个成功提示覆盖全部阶段。
