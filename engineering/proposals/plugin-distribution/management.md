# 市场管理界面与契约演进

状态：管理 API 与脚本已实现，管理网页及以下扩展尚未实现。上级：[提案总览](README.md)。

当前 [MarketAdmin](../../../projects/plugin-market/src/admin.ts) 已提供目录观测、人工刷新、带 revision 的分类/标签和可见性修改、通知查询及重试。使用方法与限制见 [Worker 项目](../../../projects/plugin-market/README.md#市场管理)。当前公开浏览网页不提供运营编辑。

## 后台界面从简

管理网页复用现有 Cap’n Web HTTP batch API，可与 Worker 静态资源一同交付。它无需完整 Pluxel Host 或 Workbench。

首版只包含实际已有的操作：

| 区域       | 操作                                                 |
| ---------- | ---------------------------------------------------- |
| 包与发行   | 搜索包、查看来源与处理结果，显式观测或刷新精确发行   |
| 运营编辑   | 修改官方标记、分类、标签和隐藏状态；按 revision 保存 |
| 任务与诊断 | 查询通知、查看可执行的重试决策、跟踪处理结果         |

版本冲突时保留编辑内容，展示当前记录供合并；页面关闭即停止读取。保存、收录与公开缓存刷新分别显示结果。已有字段足以完成首版时，使用对应表单；任意 JSON 运营规则需要先确定领域语义，不能通过通用编辑器绕过校验。

## 契约与部署更新

Worker 与工作区调用方目前共同维护 TypeScript DTO。对外发布管理客户端前，需要确定独立可导入的契约与输入 schema，去除 Worker binding 和数据库实现依赖。

需要明确契约版本、记录 revision 与 Plugin manifest 格式版本的独立含义。破坏性管理协议变更在写入前拒绝旧客户端；旧页面保留编辑内容并提示刷新。首版无需并存多套写入协议。

当前管理认证是部署方提供的管理员 token。普通用户的私有目录访问、多人管理权限与主体审计必须先有具体角色需求，再确定授权范围。客户端不能为了读取私有目录而取得完整管理凭据，见[市场客户端](market-client.md)。

## 长任务与重试

现有 `observe`、`refresh` 和 `refreshRepository` 在当前调用内执行，通知另有持久回执。若后台需要将管理刷新转为异步任务，应先确定操作身份与回执保留期：

- 同一主体使用同一请求标识重试相同内容，返回原回执；内容改变则拒绝。
- 提交响应丢失后先查询原标识；释放 RPC stub 只结束客户端等待。
- 任务回执、已接受和已完成分别表达，过期结果不能当成未执行并自动重做。

Cap’n Web batch 合并传输，不使多个管理写入成为数据库事务。多记录原子编辑只有在明确业务需求出现后才设计单独操作；关联写入继续由 D1 条件提交拥有。

## 验收条件

Agent 与管理网页通过同一公开 API 完成一次编辑、并发冲突处理和通知重试。旧客户端应在写入前被拒绝；断线、关闭页面和任务完成分别可观察。若引入异步刷新，再覆盖响应丢失后的回执查询与重复提交。
