# 文档规范与职责划分

本项目文档分为两类：`docs/` 维护面向开发者的公开使用文档，`engineering/` 维护框架内部的架构、实现细节与技术选型。文档编写以清晰、准确、自然为准则，方便人类开发者与协助工具快速上手与查阅。

## 目录与职责划分

| 目录/文件                  | 承载内容                                                    | 读者与场景                   |
| -------------------------- | ----------------------------------------------------------- | ---------------------------- |
| `docs/getting-started/`    | 快速上手、创建运行示例应用、编写第一个独立插件              | 首次接触 Pluxel 的开发者     |
| `docs/plugin-development/` | 插件模型、依赖注入、生命周期、配置、日志、测试与扩展能力    | 编写或维护业务插件           |
| `docs/host/`               | 应用装配、宿主配置、环境绑定、存储与服务部署                | 组装并部署完整应用           |
| `docs/workbench/`          | Workbench 界面、扩展视图、面板与配置表单                    | 开发可视化插件管理与业务界面 |
| `docs/development/`        | 本地工具链、开发控制台、构建打包与交付流程                  | 日常调试、本地联调与发布应用 |
| `docs/plugins/`            | 官方提供的现成插件（HTTP 客户端、认证、缓存、Typst 渲染等） | 直接使用官方生态能力         |
| `docs/reference/`          | 包矩阵、排错速查与底层 Context 参考                         | 查阅入口清单或排查具体问题   |
| `engineering/`             | 核心调度器原理、编译器 lowering 细节、内部不变量与历史提案  | 维护框架内核代码             |

每个主题在相应位置保持权威性。当相关主题产生交叉时，直接添加链接指向对应页面，避免在多处复制大段相同的配置或说明。

## 写作规范（人类化写作原则）

针对技术文档容易出现的生硬、机械与 AI 写作痕迹（参考 Wikipedia: Signs of AI writing），撰写和修改文档时应遵守以下要求：

### 1. 正向直陈，不使用负向平行对立句型

优先正面说明机制是什么、如何工作、何时生效。避免大量使用“并不是……而是……”、“X 不等于 Y”、“这不代表 Z”等否定绕弯的对立句型推进解释。若存在常见易混淆点，直接在说明后跟一句轻量提示即可，不要通篇通过反问或否定来铺陈内容。

### 2. 去除过度防御性对冲与免责套话

技术文档不是法务免责声明。删除类似“不构成性能承诺”、“不作为推断依据”、“有限语法检查不能证明……”、“所有检查通过并不保证……”等冗余对冲语言。客观陈述技术行为与结果即可。

### 3. 去除面向读者的阅读说教

开门见山切入技术主题。不要在文档开头反复指导读者“如何阅读本文”、“无需通读本文”、“读到哪里就可以开始做”。读者会根据目录和搜索自行浏览所需章节。

### 4. 主次分层，拆解分号长句

正文主干聚焦核心概念、最短完整代码和常见用法。避免把核心概念、罕见边界、编译错误码和内部校验规则用分号挤压在同一个长段落中。底层的编译器报错码（如 `plugin_caller_view_private_brand_unsupported`）与细微语法边界统一收拢在章节末尾的“注意事项”或参考列表中，保持主干阅读的呼吸感。

### 5. 破除模板化排版

- **避免机械的加粗冒号列表**：不要整页充斥 `- **标题：** 说明` 的模板化项目符号，根据逻辑灵活运用自然段落、常规列表或带有前后文的叙述。
- **杜绝滥用无意义表格**：表格仅用于真正的多参数清单、环境变量表或 API 矩阵；不要把简单的页面导航或抽象概念拆分成僵硬的表格。
- **避免强迫症式三连排比**：语言节奏保持自然，避免将每一个描述都凑成三字格或固定三个并列短语。

### 6. 使用自然的专业技术用语

减少“事实”、“契约”、“口径”、“落点”、“收口”、“承接”、“消费”等过度抽象或套路化的词汇，换用具体的“配置项”、“返回值”、“参数”、“接口规则”、“事件”等自然技术语言。

## 链接与示例维护

- 调整文档中的章节标题时，需同步检查全仓其他 Markdown 中指向该章节的锚点（`#...`），避免生成死链。
- 文档中的 TypeScript 示例应保持语法正确，Twoslash 代码块应能正常通过类型检查。
- 代码片段优先给出最短可运行示例，关键参数配合简明注释说明。
