# 文档职责与任务入口

公开文档按修改对象组织，工程文档按实现所有者组织。目标是让人和 coding agent 定位本次契约后即可修改和验证，不用先读完一套教程。

## 一处维护事实

| 内容                             | 权威位置                                | 不放在这里的内容                      |
| -------------------------------- | --------------------------------------- | ------------------------------------- |
| 第一次创建、运行与修改示例       | `docs/getting-started/`                 | 进阶 API 规则与部署策略               |
| Plugin/Part 的开发范式与能力调用 | `docs/plugin-development/`              | Host 后端选择、exporter/listener 接线 |
| 应用装配与部署配置               | `docs/host/configuration.md` 的任务章节 | 重复的插件业务实现                    |
| 自定义服务和管理接入             | `docs/host/` 对应进阶页                 | 再维护一份官方启动教程                |
| 定位、静态检查、在线操作与交付   | `docs/development/`                     | 复制领域 API 的签名和规则             |
| 页面或第三方能力                 | `docs/workbench/`、`docs/plugins/`      | 重复 Core 生命周期和 Host 通用装配    |
| 框架不变量、实现入口和回归边界   | `engineering/`                          | 普通用户完成任务不需要的通读前置      |
| Agent 能力选择与执行方式         | `.agents/skills/pluxel-development/`    | 复制上述正文                          |

同一事实只有一个权威页。其他页面说明何时需要它并链接到章节；旧正文迁移后删除，同步导航、CLI/模板/skill、README、网站入口和真实下游引用。

## 基础能力先于按需扩展

导航和最小教程先呈现依赖、事件、日志、生命周期、配置、Part 与插件测试。测试是开发基本功，教程由 `docs/plugin-development/testing.md` 维护；它使用独立测试工具，不属于 Core 运行时内建服务。明确区分 Core 自带的 `ctx.events/logger/effects`、插件声明机制、独立工具包与 Host 显式安装的服务；preset 默认安装不等于任意 Context 保证存在。

基础用法与测试集中在插件目录的第一组，HTTP、Vault、Database、worker、Workbench 属于按需扩展。第一个插件不依赖额外服务；可选页面不默认展开抢占基础导航。能力可用与输出、持久化等部署效果分开说明。事件和资源清理有独立入口，不埋在长模型页末尾。

## 写给正在完成任务的读者

- 开头说明本页解决什么、必要前提、结果和不属于本页的配置入口；复杂页面用少量任务到章节的映射。
- 按“选择规则 → 最短完整用法 → 失败/所有权 → 验证”组织相关内容。已有目标直接读对应章节，不强迫先读总览。
- 明确示例是生产应用、独立 Host、隔离 test host 还是业务方法片段；不同 host API 不混用。
- 展开会改变实现决定的边界：输入来源、默认值、是否生效、谁释放资源、取消和失败意味着什么。保留已验证细节，不为缩短篇幅删除约束。
- 原生 API 链接上游；只解释 Pluxel 的接入和差异，不复制完整上游手册。不要仅因文件长就拆页，也不要为“集中”混合不同职责。
- 路由表不是阅读清单。已明确修改点、输入和资源所有者、调用方及验证方式后停止扩展文档。

设计原则按改动范围在实现前阅读，并用于 review；不要用“遇到问题再读”把契约、失败和并发设计写成排错选项。按需阅读的依据是任务相关性，不是是否已经发生故障。

## 迁移与验证

文件移动后检查相对链接、章节锚点、meta 导航、站点 URL，以及代码字符串中的文档路径。按变更范围验证 Markdown/MDX 构建和 CLI 读取；迁移后的正文不能只在浏览器导航里可见，也应能用准确路径直接读取。

静态链接检查与一次构建只能证明可发现、可加载及示例编译范围，不能证明 agent 效率提升。声称效率提升需要独立任务评估；通常交付实际改动、入口和验证结果即可。
