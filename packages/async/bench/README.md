# Async 基准与设计复审

## 复现

```sh
pnpm --filter @pluxel/async bench
```

该命令先用 tsdown 构建并验证制品，然后使用 `vitest.bench.config.ts` 的原生 ESM 模式运行全部基准。普通测试继续从 `@pluxel/source` 读取源码，不依赖 dist；基准则断言所有本包入口解析到 dist，与对照库的 npm 制品保持同一层级。这样避免了 [Vitest module runner 的 export getter 开销](https://vitest.dev/guide/benchmarking#module-runner-overhead)。

同类库都是精确锁定的开发依赖，由 pncat 管理 catalog；本包仍无运行时依赖。报告器输出对比表及 `ASYNC_BENCH` JSON 行（均值、中位数、相对误差和样本数）。文件和场景顺序执行，`bench.compare()` 使用 Vitest 的交错测量，不设性能通过阈值或自动挑选最快重试。

## 场景与可比范围

| 文件                        | 比较内容                                                                    | 边界                                                                                                          |
| --------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `graph-peers.bench.ts`      | grfn 3.0.0：复用 diamond、构建+执行、复用 32 叶 fanout                      | 相同 async 算术和单一输出，测量前验证共享根只执行一次；默认 early，未比较失败                                 |
| `iter-peers.bench.ts`       | p-map 7.0.8 的 pMapIterable：c4、backpressure4；lfi 4.1.2 的 mapAsync：串行 | 相同输入顺序与 collector，先验证输出和 mapper 并发峰值；不把 lfi 的 push/concurrent iterable 当作相同背压模型 |
| `primitives-peers.bench.ts` | p-limit 7.3.3：共享 c4；p-memoize 8.0.0：cache:false；p-retry 8.0.1         | 最终成功的共同子集（含一次可重试失败）；不比较不等价的取消、关闭或终止失败策略                                |
| `grfn.bench.ts`             | diamond 与手写 Promise                                                      | 原生编排参考，构建/编译不计入                                                                                 |
| `concurrency.bench.ts`      | limit 与 iter                                                               | 内部机制成本；eager 接纳和有界窗口并非同一契约                                                                |

输入规模为 128 的场景，每个测量样本执行完整批次。limit 的实例创建和 close 计入；singleflight/p-memoize 的工厂创建不计入，验证同一 key 合并且完成后重新执行。iter 每次创建流并收集全部结果。重试显式对齐为最多两次尝试和相同 shouldRetry；重试失败场景统一为 1ms 延迟、无 jitter。**不比较零延迟重试**：p-retry 跳过零延迟定时器，而本包仍让出事件循环。

这些基准不覆盖慢消费者的峰值内存、等待者取消的内存释放、网络 IO 或业务吞吐；那些生命周期差异由回归测试保护。`setImmediate` 只是事件循环让步，不代表真实网络延迟。

## 2026-09-28 测量

Node 24.16.0、Vitest 5.0.2、tsdown 0.23.0；Linux x86_64，Intel Core i5-11400H。工作站未锁 CPU 频率/亲和性。三次独立进程顺序运行，每个 peer benchmark 配置测量至少 500ms/100 次、预热至少 100ms/10 次；没有 Vite export getter 告警。

这些结果不支持“本包全面更快”：

- limit 和复用后的 grfn 在这些工作负载中开销较低；grfn 每次重新构建执行则较慢，符合其编译复用定位。构建场景单轮 RME 最高约 20%，不据此给精确加速倍率。
- iter 比 pMapIterable 慢；concurrency=1 的通用调度器也明显慢于 lfi 的串行 mapAsync。只需串行处理时，用普通 for-await 或本包顺序消费端即可，不必建立并发池。
- singleflight 单 key 接近 p-memoize，多 key 本轮也较接近，但跨轮波动明显；本包还维护可移除的取消等待者与关闭契约。此表没有量化这些语义各自的成本，不能把全部差异归因于某一实现细节。
- retry 首次成功路径略慢但绝对差值很小；包含 1ms 退避时主要是定时器成本，不能据此判定重试算法性能优劣。

本轮保留两项不改变 API 的结构简化：singleflight 在首次可取消等待者到来时才分配 Set，settle 不再创建替代空 Set；iter 在已有完成/失败回调中移除在途任务，省掉每项额外的 `.then()` 和 Promise。没有新增同步源或 concurrency=1 专用调度分支。

JSON 的 `optimizationBaseline` 保留前一轮相关场景的数据。前后运行不在同一交错比较中，且对照库也有速度波动，因此不把绝对耗时变化宣称为优化的因果收益。确定的收益是减少无用分配与调度步骤，生命周期与错误回归保持通过。

没有为提高排名删除输入校验、取消通知或 drain。后续有真实吞吐瓶颈时，再以对应工作负载定位与优化。

## 设计复审结论

这是一份有边界的审查结论，不是“所有设计永远最优”的认证。

| 原则           | 当前证据／取舍                                                                                         |
| -------------- | ------------------------------------------------------------------------------------------------------ |
| 契约可读       | 六个领域子路径；retry 明确总尝试次数和重试判定；singleflight 在工厂绑定操作，调用者只提供 key          |
| 所有权明确     | limiter 持有额度直到任务真实完成；singleflight 等待者不能取消共享任务；close 停止接纳并排空            |
| 可观测、可验证 | 稳定关闭错误类型、limiter 实时计数、边界回归、公开类型和无源码制品消费；原错误不被 cleanup 错误覆盖    |
| 输入与成本边界 | 必填并发数、有限重试、定时器参数校验；limiter 排队和 keyed 总并发不设上限，文档明确建议流式输入用 iter |
| 原生协议的限制 | async generator 的 return 排在 pending next 后；要中断正在等待的 pull，调用方必须传入并取消外部 signal |
| 实用性证据     | 包级回归与 shared-requests 可运行组合示例；目前没有把新工具强行接入无关框架路径，也未证明生产业务收益  |

本次复审补齐了 pending-next 的说明与回归，并把发布 README 的使用指南、示例和维护链接改成仓库 URL，避免已安装包里的相对路径失效。没有增加新的公共工具。

最终独立复审确认上述两项简化保留任务排空、取消等待者释放和原始错误传播契约；相关运行时与类型回归均通过。
