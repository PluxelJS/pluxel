本页面向运行应用的人：先在插件详情确认当前状态，再查看最近更新和依赖。
给 Plugin 编写页面请从 [Content](./content.md) 或 [View](./view.md) 开始。

## 从现象定位问题

| 现象                 | 下一步                                                           |
| -------------------- | ---------------------------------------------------------------- |
| 插件没有运行         | 查看自动启动策略、配置校验和必须依赖                             |
| 修改源码后出现错误   | 对照当前状态与最近更新，确认是保留旧定义还是新实例启动失败       |
| 自定义页面显示构建中 | 等待构建完成；失败时按该页面显示的错误修复 renderer              |
| 页面提示会话失效     | 更新引起的失效会自动整页刷新；认证失效或连续刷新暂停时按提示处理 |
| 保存配置后行为未变   | 检查保存结果；未注册在线更新处理时需要显式重启                   |

## 工作区标签与布局

左侧固定入口栏提供首页、应用、插件管理、日志、认证与安全、安全审计和依赖图。默认仅显示图标，悬浮可查看名称，
也可切换为图标与文字。“应用”打开 `/apps`，集中列出明确声明导航入口的业务路由；“插件管理”打开 `/plugins`，用于查看运行状态、配置与依赖。
业务应用与插件管理使用独立的导航上下文，日常业务无需先经过插件配置页面。

插件管理的左侧边栏显示插件目录，按运行状态列出插件，选择后在中间编辑配置。目录使用紧凑单行列表，正常状态以圆点表示，
异常、等待启动或不可用保留文字。分组显示数量并可折叠；搜索临时展开匹配组，清空后恢复折叠偏好。长名称和来源可悬浮查看。
业务应用的左侧只显示当前所属插件提供的扩展面板；未声明左侧面板时不显示空边栏。应用目录本身不展开插件侧栏。
切到首页、全局日志、安全等官方页面时辅助工具收起，切回相关文档时恢复手动展开偏好；与文档共享的原生容器不会被整体隐藏。
目录标记当前插件，页面入口高亮匹配具体入口。边栏只放导航面板时省去重复的原生标签条；将文档拖入边栏后恢复原生标签条。

顶部“查找入口”搜索全部官方页面、插件和已发布页面入口，包括未加入常用导航的路由。
从搜索打开参数化页面时，需要先输入匹配路径模板的具体路径；标记为“独立页面”的入口会离开工作区，在完整页面中打开。
右侧插件信息默认收起，显示当前活动插件的状态、依赖和日志级别。插件日志默认不打开，点击顶部“底部面板”按钮后，在中间文档区下方打开原生日志窗格，不横跨左右侧栏。切换中间的插件文档或发布页面时，信息和日志跟随所属插件
（包括 fork）；点击辅助工具保留这个上下文。全局日志从固定入口栏的“日志”打开。
顶部正中的布局按钮分别控制左侧导航、右侧面板和底部面板。右侧和底部默认内容分别为插件信息、插件日志，也能切换到当前插件声明的面板。左右侧栏再次显示时恢复收起前选择的标签。顶部“底部面板”按钮收起时保留其布局信息，再次显示会恢复原位置；原位置无法恢复时在中央文档区下方重新显示。直接关闭日志标签才移除日志工具，同一窗格内的其他文档保留。
这些操作不丢弃文档输入；日志收起、关闭或因其他容器最大化而隐藏时停止订阅。
普通入口会复用并聚焦已有文档；标签栏的“+”统一打开“新建标签页”选择器，选择入口后在该容器创建独立文档。入口列表不再逐项显示副本按钮。每个文档保留自己的页面导航和输入；地址栏跟随活动文档，
工具获得焦点时不会替换它的地址。浏览器前进、后退由工作区统一协调。

内置页面使用各自的默认标签，插件详情使用已发布的插件名称，独立插件页面使用声明的标签或路由标题；
没有声明标签时使用入口 key。可用 `F2` 重命名标签，未改变页面身份的查询、锚点变化、重新激活和布局刷新会保留手工名称；
切换到不同页面或入口时使用新的默认名称。
从标签右键菜单打开副本时，名称为当前名称加“（副本）”，副本有独立输入。从“+”选择入口创建的文档使用入口的默认标签。

标签、容器和边栏使用原生停靠布局：拖动标签到其他容器，或拖到边缘拆分；拖动分隔线调整尺寸，最大化当前容器以专注内容。
右键菜单可固定标签、加入或建立分组、调整组名和颜色、折叠组、移动与关闭。折叠和移动只改变布局，页面 API 与订阅仍属于原文档。

固定标签从所在分组移到容器的固定标签区；取消固定不会自动回到原组。分组名和颜色标识标签的 UI 分组，
不会改变插件目录分组、publication 分类或插件依赖。

“关闭可见且可关闭标签”“关闭其他可见标签”和“关闭右侧可见标签”只作用于当前标签栏中可见的候选，不包含折叠组的隐藏成员。
关闭整个容器会检查包含折叠分组在内的原生可关闭候选；固定或不可关闭标签及受保护分组会保留，所在容器也可能继续存在。
“关闭分组内全部标签”“关闭所有文档”和恢复默认布局要求先解除目标的固定或关闭保护。
未保存输入会先请求处理，取消或保存失败会保留文档。
批量删除在内容守卫拒绝时保留全部目标；已经完成的业务保存不会因此回滚。

窄窗口首次默认收起左侧导航，使用标签溢出菜单、边栏与最大化找回内容，不自动重排已保存的布局。工作区菜单可恢复默认布局，或打开插件目录；业务应用从“应用”入口选择，顶部查找入口也可重新显示插件目录。
重置前需要处理未保存文档。布局保存标签、分组、尺寸、文档地址、入口栏显示模式和导航面板所选视图，不保存未提交的配置或表单草稿。
本次布局升级不读取旧版布局，首次使用从默认布局开始；未提交的草稿不会迁移。当前版本的布局恢复失败时，
会保留快照并显示重试或显式重置入口；存储失败不阻止继续使用当前工作台。

### 键盘操作

`Mod` 表示 Windows/Linux 的 `Ctrl` 或 macOS 的 `⌘`。顶部工作区菜单也提供“键盘操作”帮助。

| 按键                          | 操作                                 |
| ----------------------------- | ------------------------------------ |
| `Mod+P`                       | 查找全部页面、插件入口和固定工具     |
| `Mod+B`                       | 显示或收起左侧边栏                   |
| `Mod+W`                       | 关闭活动文档，遵守固定和未保存保护   |
| `Mod+Shift+[` / `Mod+Shift+]` | 按原生布局顺序切换上一个或下一个文档 |
| `Mod+Shift+M`                 | 最大化或还原活动文档所在的中央容器   |
| `Shift+F10` / 菜单键          | 打开所聚焦标签、分组或容器的菜单     |
| `F2`                          | 重命名所聚焦标签                     |
| `Ctrl+Delete`                 | 关闭所聚焦标签                       |
| `F6`                          | 在所选标签和内容间切换焦点           |
| `Ctrl+F6` / `Ctrl+Shift+F6`   | 聚焦下一个或上一个标签容器           |

工作区命令在文本输入和菜单打开时暂停；查找入口可在输入时使用。原生标签和菜单保留自己的箭头键、确认与退出操作。
配置页面的 `Mod+S` 保存当前配置，`Mod+Shift+S` 保存当前插件的全部脏配置；保存结果由业务 API 决定。

插件还可声明[左右侧栏与底部面板](./panels.md)。区域内的横向标签只列出当前插件的面板；选择它们不改变中心文档地址，隐藏或切换后临时输入不保证保留。

## 内置依赖管理

插件概览用同一张「依赖管理」卡片展示必须依赖、可选集成、提供的能力和被依赖关系。依赖抽象能力时，
依赖行同时显示需求与实际实现，例如 `Cache → CachePlugin`。

- **当前插件使用**：只设置当前插件的这条必须依赖。具体插件的「默认实例」使用该插件的默认节点；
  抽象能力的「跟随全局默认」使用该能力的全局默认实现。手动指定实现或 Fork 后，显示「当前插件指定」。
- **提供的能力 / 全局默认实现**：设置该抽象能力的默认提供者，影响所有未单独指定实现的消费者。
  当前插件就是该默认实现时，显示「全局默认提供者」。

单独指定的实现优先于默认选择；恢复默认会移除当前插件的覆盖。修改依赖可能重启受影响的插件及其下游。
修改后，工作台刷新依赖图和已打开的依赖编辑器，未打开的编辑器在下次打开时读取最新设置。

## 内置 Plugin 目录诊断

“插件管理”页面的目录行优先显示插件名称，不重复铺开包名、HMR badge 或运行状态文字。小菱形表示更新类别，小圆点表示运行状态；
悬浮或键盘聚焦指示器可查看具体说明；悬浮或聚焦插件名称会按行展示完整名称、来源、导出、状态、更新方式和 canonical reference。
分组标题只显示淡色数量，悬浮可查看运行数量；
更新异常仍保留警告图标。完整执行与来源信息在插件详情中展开查看。

来源取自插件定义，不会因为没有 HMR 信息而变成“未知来源”；静态内置插件也可能使用构建模块，来源与是否 HMR 是两件事。

Plugin 详情默认只展示简短说明（有则显示）、状态和来源。来源旁可以复制插件引用；执行方式、制品、更新边界、启动策略与
最近更新放在默认折叠的“调试信息”中，没有更新记录时不显示空占位。“复制诊断信息”可一次复制引用、执行和更新事实、
运行状态及问题代码，便于排查；不会复制 Vite module ID、绝对文件路径或包安装目录。

顶部更新指示器展示最新批次，点击可查看阶段、触发文件、原始原因摘要和可用的导入链。失败的新插件尚未出现在目录时，仍会在此显示原因。
更新状态通过已有会话订阅；失败结算也会刷新目录诊断，不需要手动刷新列表。

工作台分别显示当前运行状态、本插件上次更新记录和所属更新批次。一次应用或插件批次更新可以已提交，
同时只有部分插件的生命周期失败；正常插件不会因此标红。具体错误按插件节点归属，包含失败阶段、原因和阻塞它的依赖；
同一插件的不同 fork 分别记录。资源清理异常也属于上次更新历史，不能据此推断新实例没有运行。

“未报告生命周期”表示该次更新没有这个节点的完整执行报告，不代表启动成功。已修复的运行问题不会改写历史；
是否已恢复应看当前状态。调试信息保留所属批次的范围、结果和序号，便于关联同次更新。提交前失败会说明保留旧定义，
应用重载失败后成功创建补偿宿主会说明使用上一应用定义恢复。

自定义管理客户端分别读取 `recentUpdate.batch` 和 `recentUpdate.lifecycle`：前者记录更新批次结果，
后者记录本插件的历史生命周期问题。`lifecycle: null` 表示未报告；`{ issues: [] }` 表示该批未报告异常。
判断插件是否可用仍需读取当前运行状态。

自定义客户端通过 `client.updates.snapshot()` 读取独立批次，或 `client.updates.follow(observer)` 订阅当前值及后续变化。
返回的 `Disposable` 由调用方在页面卸载时释放；它借用同一条 Management 会话。快照包含递增 `sequence`、
`state`（updating / settled）、阶段、结果、耗时、触发文件及错误摘要。没有更新记录时为 `null`；它不是每个插件的当前健康状态。

“目录 HMR”表示应用模块图变化时热替换插件目录；入口或应用配置边界变化仍需重建应用。外部包通常显示“入口 HMR”：
替换插件入口可以触发更新，但不会监听包内部源码；只有确认源码在监听图中时才显示“源码 HMR”。制品信息无法确定时显示“未报告”，
不从扩展名或包路径猜测。

正常工作区导航不会重建整个工作台；各个文档拥有自己的插件表单和视图，相同插件可以在多个独立文档中打开。
会话失效或插件发布更新导致的完整刷新仍遵循原有生命周期规则。
单个页面渲染失败会在对应文档显示错误与“重试”，其他文档和工作台导航保持可用。

“插件管理”页面的目录搜索支持以下字段；多个 token 使用 AND：

- 普通关键词：名称、定义位置、导出名、canonical reference 和 execution 词；
- `@包名`：只匹配 definition address 中的 package name；
- `ref:关键词`：只匹配 canonical reference；
- `exec:关键词`：只匹配制品、更新方式和最近结果，例如 `hmr`、`next-start`、`bundle`、`restored-previous` 或“失败”。

## 生命周期和故障

同一 document 只有一条 `/__pluxel/runtime/session` WebSocket。认证 challenge、Management、Workbench layout、
Plugin API 和 observer 都复用这个 Cap’n Web session。认证或 publication epoch 失效、socket broken 时，页面要求完整
reload；不会在原 document 内切换 transport、重连一部分功能或复用旧 API root。

MF2 manifest 和 JS/CSS 仍通过 HTTP 获取；Content plan 则随现有 `openEntry()` RPC 返回，不增加浏览器 artifact
fetch。浏览器写入 `HttpOnly` cookie 还有一个 single-use cookie-commit POST。这些端点不承载 Workbench RPC。

Plugin stop/replacement 会撤销 publication，并使当前 socket epoch 失效。Shell 销毁所有 active Bridges、释放 opened
handles，再要求整页 reload。开发期 Content/topology 可以先发布，缺失 producer 在后台构建；未就绪或失败的 View/Attachment
placement 会保留在原位置并显示构建中或构建失败状态，producer 成功提交后触发 reload。Production/static build 仍要求
Content/MF candidate 全部验证并原子提交后才生效。

保持 Vite dev 运行时，可以修改独立 `workbench.ts`，在 `workbench.content()` 与 `workbench.view()` 之间切换，
或更换 renderer；相应的 `publish()` bindings 也必须符合新定义。源码暂时出错时，修正并保存即可触发下一次更新。
Host 的 Vite 开发同样处理定义文件的删除与重新创建，无需重启 dev。若更新导致插件初始化失败，后续有效更新会自动恢复
仍需运行的插件及其依赖方；手动停止的插件仍保持停止。

Bridge destroy 也会关闭 per-open renderer owner：私有 `QueryClient`、subscription 与 active mutation lifetime 一次清理。Pending
`refetch()` / `mutateAsync()` 会以 closed error 及时拒绝；无法取消的 RPC 可以在后台 settle，但晚到的 fulfilled DTO 仍会
consume/dispose，且不会再更新已关闭页面。Portable/scope/key/limit/closed 与 mutation-pending 错误提供稳定 code；Plugin
自己的领域/RPC error 保持原样。

Plugin 启停命令的 `ok: true` 表示运行意图与 graph commit 已应用，不保证每个 `init()` 或 drain 都成功。Workbench 会继续读取
`report.core.summary.lifecycleReport`：目标 Plugin 有结构化 lifecycle issue 时直接显示该 issue 的安全 message；只有 report 没有
可解释当前节点的 issue、但观察状态尚未达到目标时，才显示“运行状态仍未收敛”的协调提示。

## Vite 与反向代理

Vite 开发接入在 Vite 自己的 Node listener 上接入 Runtime HTTP/Upgrade，并先让 Vite HMR socket 匹配；开发者
不需要为 Workbench 再启动或代理一个端口。

生产反向代理只需保留同源路径并正确转发 WebSocket Upgrade：Workbench document、`/__pluxel/` HTTP endpoints、MF assets
和 `/__pluxel/runtime/session` 应到达同一个 Runtime deployment。Runtime 不相信 `Forwarded` / `X-Forwarded-*` 推断
physical TLS 或 locality。内建 production Node launcher 只监听 HTTP，因此默认只通过 loopback/SSH tunnel 管理，不通过普通
TLS 反代开放 remote Management，反代也不应从 loopback 地址回源。需要 remote Management 的平台集成必须提供自身能证明
HTTPS 的 application carrier。多实例部署还需要让 control socket、OIDC callback 和短期 cookie ticket 命中签发它们的实例。

## 插件详情与内容目录

插件配置在中间文档中编辑；状态、依赖和日志级别位于右侧插件信息，插件日志位于底部。
业务 publication 入口另行打开为工作区文档，可以独立排列和关闭；工具区跟随与显隐方式见[工作区标签与布局](#工作区标签与布局)。

配置项或 Markdown 标题存在时，文档内可以显示搜索和层级目录，点击目录定位对应内容。
目录只读取当前内容区域，不扫描其他文档或远程页面；没有目录项时不显示空面板。
