# Plugin Workbench Design

## Goal

插件工作台的目标不是“把 `/plugins` 页面做复杂”，而是把插件运维最常见的一条链路压缩进一个连续工作面：

1. 找到插件
2. 查看状态和来源
3. 修改配置
4. 保存并重启
5. 立即看日志和诊断
6. 继续调整

设计优先级始终是：

- 操作连续
- 信息密度高但不拥挤
- 高频动作一眼可见
- 面板结构稳定，便于 MF2 / 动态扩展持续接入

## Layout

当前工作台固定为四区：

- 左侧 `activity rail`
- 左侧 `section pane`
- 中间 `workspace`
- 右侧 `context rail`
- 底部 `dock`

其中中间 `workspace` 再分两层：

- 第一层是运行控制带
- 第二层是页面内容标签带

这样拆分的原因很直接：

- 运行控制是一级高频动作，不能和内容标签挤在一行
- 标签只负责“当前在看什么”，不负责“我要怎么操作插件”
- 右栏只承载上下文和诊断，不再承载主操作

当前已落地的容器角色：

- 最左是 `global activity`
- 左侧是 `route-owned section pane`
- 中间是 `editor area`
- 右侧是 `sidebar tab container`
- 底部是 `panel tab container`

## Extension Hierarchy

这次重构后，四个边界不再按“左中右下”粗暴理解，而是按作用域理解：

- 最左 `activity rail` 是全局工作台扩展位
- 左侧 `section pane` 是当前一级路由自带的工作区导航位
- 中间 `editor area` 是当前任务文档位
- 右侧 `sidebar` 和底部 `panel` 是当前 editor tab 的情境扩展位

这比“左边也算插件页的一部分”更实用，原因是：

- 最左永远承担全局切换，不应被某个插件页接管
- 左侧次级导航由当前一级路由决定，例如 `/plugins` 显示插件列表，未来 `/packages` 也可以换成包过滤器
- 右侧和底部跟着当前 editor tab 走，才符合“改配置后马上看日志 / 诊断 / outline”的工作流

依赖跳转也遵循这个原则：

- 在详情里点击依赖，默认新开 tab
- 不覆盖当前正在编辑的插件页
- 更符合“参考别的插件，再切回当前插件”的操作节奏

因此当前推荐的职责划分是：

- `global`:
  activity、全局状态、全局命令入口
- `section / route-owned`:
  左侧次级导航、筛选、对象选择
- `editor-context / plugin-context`:
  `plugin:tabs`、`plugin:context`、`plugin:dock`、outline、日志、工具视图

这里最关键的一点是：

- 左侧次级导航不是全局扩展
- 也不是插件情境扩展
- 它是当前工作区 section 自己的壳层结构

这样未来就算插件工作台继续重构，左侧对象选择区和右侧/底部情境区也不会继续互相污染。

## Core Decisions

### 1. 插件导航和工作内容分离

左侧插件列表只回答“我要操作哪个插件”，中间标签只回答“我当前在做什么”。

所以：

- 左侧列表适合快速切换目标插件
- 中间标签适合保留当前任务上下文
- 右侧上下文栏不再承担导航职责

### 2. 日志必须和主任务共存

改配置之后通常马上要看日志，因此日志不能再是独立主页面。

底部 `dock` 的职责就是承接这类验证信息：

- 实时日志
- 日志级别调试
- 运行输出扩展
- 后续可接入的最近操作反馈

日志默认保留在当前任务下方，而不是把用户赶去另一个路由。

### 3. 目录不再做全局浮层

之前的 TOC / 浮动目录会遮挡内容，也会和右栏竞争空间。

当前设计里：

- 配置表单 TOC 只存在于右侧上下文体系内
- 插件页面辅助通过 `assist host` 进入右栏
- 主工作区只留给当前任务内容

### 4. 分栏尺寸按工作台全局记忆

左右栏和底部 dock 的尺寸现在按工作台全局记忆，而不是按插件单独记忆。

原因：

- 用户对“插件详情页”的空间偏好通常是稳定的
- 切插件时尺寸突变会破坏操作节奏
- 统一尺寸更接近 IDE 的工作面预期

### 5. Tab 策略默认复用，明确新开

工作台顶栏 tab 的设计重点不是“越多越像浏览器”，而是避免无意义堆积。

当前策略：

- 普通点击默认复用当前 tab
- 插件列表项提供明确的“在新标签页打开”入口
- 如果当前 tab 存在未保存配置，普通点击会自动改成新开 tab，保护当前修改
- 如果目标已经在其他 tab 打开，则直接激活已有 tab
- 关闭 dirty tab 会要求确认

这是当前最实用的平衡：

- 浏览插件时不会把 tab 栏刷满
- 真正需要并行对比时有显式新开入口
- dirty 页面不会因为误点列表而被覆盖

### 6. 主操作必须前置

启动 / 终止 / 重启 / 持久启用是插件工作台里最常用也最昂贵的动作。

因此它们现在固定在主工作区顶部，形成单独的运行控制带，并且：

- 使用带文字的按钮
- 同行展示运行态 / 持久启用态 / 同步态
- 扩展头部内容只作为附加信息，不压住主操作
- 主内容区不再承载“日志级别”这类运行验证工具 tab

同时，中间主工作头允许直接显示插件名与来源信息。

这样更实用，因为用户进入插件详情时最先需要确认的是：

- 当前操作的是哪个插件
- 它来自 HMR 还是包安装
- 它依赖谁

### 7. 减少重复标题，优先把空间还给内容

当前工作台不再追求每个面板都重复写一遍标题。

现在的规则是：

- 顶层 topbar 负责说明当前所在工作区
- 顶栏 tab 负责说明当前打开的任务实例
- 中间主工作头保留插件名与来源，因为这是任务上下文，不算冗余标题
- 右侧和底部优先保留 tab strip，本地标题能省则省
- 面板内工具不要再重复写“日志 / 级别 / 上下文”这种已经由 tab 说明的信息

这样做的目的不是极简，而是把有限高度让给：

- 配置表单
- 日志滚动区
- 右侧上下文信息

## Extension Placement

当前扩展点分层如下：

- `navbar:items`
  放入最左全局 activity rail
- `plugin:tabs`
  放入主工作区内容标签
- `plugin:header`
  放入运行控制带右侧补充区
- `plugin:context`
  放入右栏上下文区
- `plugin:dock`
  放入底部 dock
- `plugin:info`
  放入右栏概览区的宿主扩展位

这样分层的原则是：

- 全局扩展只能影响全局 rail，不干预具体工作区布局
- section pane 由当前路由壳层拥有，先不开放给插件动态改形
- 动态扩展只能进入稳定 pane 内部
- 外层 pane 树不允许被插件在运行时随意改形
- 扩展应该补充宿主布局，而不是反过来主导宿主布局

更具体地说：

- 最左 activity 是 host-managed global area
- 左侧 section pane 是 route-managed area
- 右侧和底部才是 plugin-context extension area

## Practical Trade-offs

### 为什么没有做浏览器式无限 tab

因为插件运维不是网页阅读。

如果每次点击列表都默认新开：

- tab 很快失控
- 关闭成本升高
- 当前任务层级会被稀释

所以默认复用更符合“工作面”而不是“浏览器历史”。

### 为什么先做 tab 状态缓存，而不是整页 keep-alive

当前真正影响体验的不是“组件有没有卸载”，而是“卸载后用户刚才的工作有没有丢”。

所以这轮优先保证：

- 何时复用
- 何时新开
- dirty 如何保护
- 关闭如何确认
- 右侧内容页、schema 选择、配置草稿能按工作台 tab 恢复

其中未保存草稿只在当前会话内保留，不写入本地持久化存储。

这样后续如果再补整页 keep-alive，也是在一个已经稳定的 tab 生命周期模型上加速，而不是用缓存去掩盖交互设计问题。

### 为什么右栏不放主操作

右栏天然是次级阅读区：

- 适合状态摘要
- 适合诊断
- 适合辅助导航

不适合承担最重要的启停动作。

把主操作放在右栏会导致：

- 发现成本高
- 横向空间被压缩
- 运行态和主任务割裂

## Current UX Rules

当前工作台的稳定规则如下：

- `⌘/Ctrl+B` 切换插件列表
- `⌘/Ctrl+K` 聚焦插件搜索
- `⌘/Ctrl+W` 关闭当前工作台 tab
- `⌘/Ctrl+Shift+[ / ]` 切换前后 tab
- 关闭 dirty tab 前弹确认
- 插件列表项右侧 `+` 为明确新开 tab
- 当前 tab dirty 时，普通点击插件列表默认自动新开
- 右侧栏显隐按当前 editor tab 记忆
- 底部 dock 显隐按当前 editor tab 记忆
- 左侧 section pane 显隐按 section 记忆

## Known Limits

当前设计已经稳定，但还保留两项明确限制：

- 顶栏 tab 目前是“状态缓存优先”，不是完整 keep-alive，切不同路由仍会重新挂载页面实例
- dirty 保护和草稿恢复目前重点覆盖配置工作流，其他可编辑扩展页后续也要接入同一套 tab state 机制

这两点都属于可继续演进的实现问题，不影响当前交互模型成立。

## Next Model

如果进入下一阶段，不建议继续在当前 `plugin:tabs / plugin:context / plugin:dock` 上打补丁。

下一阶段的目标模型见：

- `docs/design/plugin-workbench/extension-model.md`

核心方向是把扩展从 slot 注入改成宿主主导的 `WorkbenchView`：

- 中间 `editor`
- 右侧 `sidebar`
- 底部 `panel`

三个区域都可以 tab 化，但语义各自独立。

其中：

- 中间 `editor tabs` 负责页面实例，可多开、可关闭、可 dirty 保护
- 右侧 `sidebar tabs` 负责辅助视图切换，默认不做多实例管理
- 底部 `panel tabs` 负责日志和工具视图切换，`Logs` 是宿主固定保留项

更完整的右侧 / 底部 tab 设计见：

- `docs/design/plugin-workbench/extension-model.md`
