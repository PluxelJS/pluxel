# Invoice orchestration boundaries

`InvoicePlugin` owns one admission/deadline scope across recognition and verification. It depends only on the public `PlaywrightPlugin` browser capability. Fiscal and tax flows are private adapter functions, not separate plugins or packages. The orchestrator selects an adapter from a validated discriminated input, never from an arbitrary model-provided URL. Credentials belong to owner-scoped Vault; image bytes are copied, bounded to 10 MiB and signature-checked. Model responses are bounded to 1 MiB, content to 16 KiB, and candidate values to 256 characters. No provider body, credential, model reasoning or invoice value is logged by the plugin.

Recognition checks the full completion, parses one JSON object (optionally a whole Markdown fence), then validates document fields and exact integer-cent arithmetic. It does not salvage truncated JSON, pad identifiers, or turn model assessments into verification. Input recognition failures are review judgments; transport/protocol and lifecycle failures reject. HTTP errors expose status without provider response text. The original native fetch/Playwright failures remain exceptions. There is no fallback to another model and no automatic request retry.

Each accepted operation belongs to its caller and plugin generation. Stop/cancel aborts fetch and closes its browser context; a borrowed human callback must cooperate with its signal. The plugin stops waiting for a non-cooperative callback and observes late rejection. Cleanup is awaited and cleanup failure alongside operation failure preserves both errors. Browser acquisition/closure still inherits the connector's lack of a hard cleanup deadline. Both adapters borrow the same per-call Page and signal; neither owns a second configuration, admission counter or cleanup scope. Config and Vault credential changes require restart.

## Challenge and test boundaries

Automatic solving is limited to the tax adapter's text CAPTCHA and includes its instruction. Only the image crop goes to the model; invoice data is not included in the CAPTCHA prompt. Both the image source and instruction text are checked after recognition and after filling, before submission. A changed challenge yields manual action without submitting the old answer. An unclear answer can use the once-only public `onCaptcha` callback, which receives PNG bytes, instruction and cancellation signal and returns text or null without a Page. Automatic rejection can also fall back to this callback after the configured submission budget. Retry is allowed only for exact explicit incorrect-code messages, bounded to at most three submissions; network errors, timeouts, quota responses and unknown messages are never retried. Fiscal interactive challenges use the common human callback; no slider/click challenge solver is claimed.

Normal tests use a real test host, dependency lowering, public Vault bindings and external fetch/browser SDK substitutions. Browser tests additionally launch Chromium against synthetic intercepted HTML to cover the real calendar controls, screenshots, field selection, result comparison, CAPTCHA attempt bounds, manual callback and context cleanup. The opt-in live test exercises the same public plugin through a real host, real model requests and real website pages. Test-owned browser launch is separate from plugin runtime provisioning.

These observations do not establish reliable automatic CAPTCHA recognition; deterministic lifecycle tests and live model accuracy are separate evidence.

## Data ownership and interpretation

`InvoiceInput` owns the minimum portal query contract. `InvoiceDetails` owns business data independently of provenance: tax buyers/sellers and monetary totals, fiscal payers/payees and amount, and shared line items/remarks. `extract()` returns a model-only details snapshot and its validated query projection. `verifyImage()` retains that complete extraction alongside verification; official data never fills a model null, nor vice versa. Recognition intentionally transcribes only query identity and the three tax amounts needed for arithmetic validation, retaining those amounts in its details rather than discarding them.

A match has one shape for both adapters: typed details, raw `InvoiceEvidence`, `InvoiceDetailIssue[]`, check time and the red-letter observation. It no longer duplicates the same identity under `ticket` and `invoice`. Business fields use stable English names; callers need not interpret Chinese labels or table indexes. Null means no usable observation, a blank string is an observed blank text, and an empty item list requires an observed header-only table. Model/portal missing data is never guessed.

`portal-snapshot.ts` is one self-contained Playwright DOM callback shared by both adapters. It bounds source evidence and samples identity and evidence atomically before the session is closed. Adapters own portal navigation and identity matching. `details.ts` performs pure, independently tested interpretation of evidence after identity matching; money/date primitives live in `values.ts`. There is no adapter registry, provider framework, extra plugin or second model pass.

Normalization accepts only unambiguous labelled fields and rectangular item tables with recognized headers. Reordered columns are interpreted by labels, not positions. Unknown columns remain in evidence; duplicate columns/tables, merged body cells and repeated headers yield null items with an issue, never silently omitted rows. Decimal strings retain precision and zeroes; explicit currency prefixes are removed only for known money fields. Masked or invalid numbers stay null with their raw text in evidence. Contradictory official totals are reported, not repaired. Identity matching and supplementary mapping issues are separate judgments. Truncated evidence is not promoted into apparently complete business values.

The current official HTML replay yields buyer/seller names and tax identifiers, all four amount fields and one typed eight-column item, with no mapping issues. Raw evidence retains 13 labelled fields and the original table. This validates that saved layout, not a new online verification or every invoice type. Sensitive values remain in ignored local evidence only. Unloaded annexes, virtual rows and image-only content remain outside the DOM observation; untruncated evidence is not a completeness guarantee.
