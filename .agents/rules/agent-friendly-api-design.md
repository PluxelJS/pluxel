# 面向 coding agent 的 API 设计

本页用于设计和评审库、SDK、插件能力与工具入口时，判断 API 是否容易被正确发现、编写、组合和修复。
它补充 [Library API Design Rules](library-api-design.md) 的决策方法，不替代其中的正确性、兼容性和所有权规则，
也不规定某个提案必须被实现。项目约束与已有公共契约优先。

## 1. 目标是少猜测，不是少几个字段

对 coding agent 友善的 API 应让它能从名称、类型、短示例和错误反馈推导下一步。
这通常也改善人的使用体验，但效果应通过实际任务验证，不能把“模型喜欢”当作设计证据。

优先检查五件事：

1. 能否找到唯一的默认入口。
2. 能否在调用处判断输入、输出和副作用。
3. 错误能否导向明确的修正或恢复动作。
4. 能否把两个操作组合起来而不丢失失败与状态。
5. 能否知道资源何时失效、谁负责等待和清理。

如果缩短 API 使这些问题只能靠阅读实现回答，就没有降低总成本。

## 2. 同一语义给一个默认入口，不同边界保留区别

**默认：** 一个动作只有一种标准写法；不增加同义别名、相同职责的 facade 或缺乏选择条件的平行模式。
用户不应在 `run`、`execute`、`invoke` 之间猜哪个才是推荐入口。

**必要区别：** 同步值与异步 IO、定义与发布、名称查找与固定句柄、本地对象与远程数据、撤销与等待退出可能具有不同契约。
它们可以拥有不同入口，但选择条件必须由真实任务决定，并在文档里给出一个默认。

| 任务事实                     | 选择依据                     |
| ---------------------------- | ---------------------------- |
| 普通业务计算或本地复用       | 先使用有类型的普通函数/方法  |
| 需要发现、输入校验和协议投影 | 使用项目既有的命令或工具契约 |
| 需要动态按名称查找           | 才引入 registry              |
| 需要远程发布                 | 才进入 transport 与授权边界  |
| 需要独立状态或资源寿命       | 才返回拥有明确清理责任的对象 |

这是一套选择方法，不要求在已有成熟 SDK 外面再包一层。原生 API 已表达这些语义时直接复用。

## 3. 名称和结构应解释真实作用

**默认：** 名称说明动作，参数说明变化因素，返回值说明完成事实。对象层级承载真实范围，包边界承载真实依赖。
完整调用表达式已经足够明确时，不追求更长的名字。

- `publish` 应确实开放某个入口，`register` 应确实改变某个目录；谁撤销、撤销什么必须明确。
- `createSession` 若涉及异步启动，就诚实返回 Promise；不能为短示例把启动故障延迟到后续调用。
- `library.notebook(id)` 若固定资源范围，返回对象有意义；只有转发作用的无参中间对象通常可以省去。
- `setEnabled(true)` 已经表意，不必把每个 boolean 都变成枚举。

**引入新概念前回答：** 它拥有哪项状态、哪条不变量、哪段寿命或哪种独立策略？如果没有答案，先使用函数、字段或内部实现。
有真实边界时则保留它，不把授权、发布和资源管理挤进一个“万能执行器”。

## 4. 明确每个事实的唯一来源

先列出作者需要维护的事实及其所有者：输入约束、业务实现、操作说明、权限、协议输出、生命周期。
能从已有事实可靠推导的内容由库生成；协议独有的信息由该协议维护；无法推导的内容不假装已经自动生成。

例如 TypeScript 返回类型不能自动成为运行时 output validator；JSDoc 不会自然出现在执行中的 class 上；
类型中隐藏成员也不构成远程权限控制。构建制品需要与真实发布绑定，不支持的形态应给出明确诊断。

删除一个字段时，继续追踪原有责任去哪里：

| 删除后发生的事                   | 判断                 |
| -------------------------------- | -------------------- |
| 从现有 schema 或类型可靠推导     | 通常减少重复维护     |
| 只在实际协议边界需要，移到该处   | 通常收窄耦合         |
| 每个调用方都要补同一个分支或转换 | 复杂度可能只是转移了 |
| 原来保护的不变量无人负责         | 不能按“简化”合并     |

四字段、一个对象或零配置可以是当前方案的结果，不能成为压过真实需求的目标。

## 5. 让类型和反馈参与编写过程

**默认：** 已知本地数据给准确参数类型，外部输入进入时运行时校验，handler 使用校验/解码后的类型。
静态类型与运行时校验各有职责；有类型的方法仍然可以并且常常需要运行时校验。

当一个公开入口有意接受 `unknown`，文档应说明它是接收 candidate 的边界，不能同时声称参数拼写受编译器保护。
增加 typed overload 后仍保留 `unknown` overload，不会让错误输入变成编译错误。
不要为绕过校验再加 `unsafeExecute`；优先确认调用方究竟需要输入边界还是普通业务 API。

类型验收应覆盖真实编写动作：参数补全、错拼字段、省略必需 context、同步/异步返回推导、失败分支缩小、wire/decoded 差异。
不要只证明泛型能写出来；通过 `as any`、显式填写所有类型参数或手写重复接口才成立的示例不算默认路径验证。
组合多个操作时，还要用异构数组、方法表和预声明变量验证完整约束；满足其中一个成员，不代表满足整个集合。

运行时诊断应包含安全的错误分类、位置与必要上下文，让调用方知道应该改参数、重新发现、取得权限还是终止。
未知异常保留诊断链路；稳定 code 供程序分支，message 解释问题，不能让调用方解析 message。

## 6. 用组合场景检验错误契约

**默认：** 先确定失败后调用方要做什么，再选择领域 Result、异常或协议错误；沿用成熟 SDK 和已有领域回执。
在同一边界提供一种标准处理方式，不强迫框架所有边界返回同一种 envelope。

对于自有的、接收待校验输入的执行边界，输入错误和业务拒绝都是调用方需要处理的正常结果，默认在返回类型中显式建模。
`command.execute()` 已经表达明确行为；为了少一个 Result 而让每个调用方用 try/catch 重建失败分类，会增加总复杂度。
采用 Result 时，作者与调用方遵循同一约定：显式产生成功/失败、直接转发已有结果，框架不再次包装；窄领域错误在协议边界显式投影。
明确哪些未知异常由此边界监督并转换、哪些仍会 reject；返回 Result 这一类型本身不是永不抛出的保证。
配置、SDK、资源创建和清理按各自职责选择契约，不因一个执行入口采用 Result 就机械统一。

至少写出这些调用点：

- 一个操作正常返回。
- 一个预期业务失败可以被分支处理。
- 一个外部依赖意外 reject，诊断未丢失。
- 第二步依赖第一步结果，失败时不误执行后续步骤。
- 批量部分成功，已完成的结果仍可判断。

如果 handler 返回值与公开入口返回值不同，必须在最短教程明确。不得根据对象含 `ok`、`error` 等字段自动猜测控制语义。
若使用内部 throw 的终止 helper，说明普通 catch 仍会捕获它；若使用 Result，说明它不会自动阻止调用方启动下一项任务。
不要用额外 `unwrap`、`tryX`、`xOrThrow` 弥补一个尚未确定的主契约。

执行失败、业务拒绝、部分成功、结果编码失败和取消可能需要不同恢复动作。
尤其是写入已经发生、结果未送达的情况：应提供领域确认路径或诚实的不确定结果，不把它描述成可安全重试。
幂等性来自业务协议，不来自名字、annotation 或统一包装。

## 7. 让资源与时序有可预测的默认

**默认：** 普通定义不拥有运行资源；发布句柄明确撤销范围；session 等资源拥有明确关闭过程。
沿用项目的 effects、`using`、`await using` 或原生清理协议，不再制造同义生命周期机制。

一份契约需要能回答：

- 创建是否立即产生副作用，失败时是否留下资源。
- 撤销是否只拒绝新调用，已接纳工作如何处理。
- 取消是停止等待、请求协作停止，还是确实终止工作。
- 清理是否等待工作退出，重复/并发清理如何完成。
- 缓存句柄、子对象和权限变化后还能做什么。

`Promise.all` 提前失败不等于其他任务已停止；销毁客户端也不等于服务端工作已退出。
库负责跟踪它接纳的工作，业务负责等待它自行启动的 IO。无法提供的 drain、回滚或 exactly-once 语义应直接说明。
取消是停止请求，不能自动覆盖已经取得的领域回执；取消与未知故障同时出现时也要保留真实故障原因。
异步权限检查或 context 准备持有资源占用，不等于业务已经接纳；最终分派前复核发布、会话和 owner 状态。

权限和文档发现也要区分：拿到类型不授予权限，重新发现不自动扩大批准范围。
类型、动态属性访问、缓存 callback 与子引用必须服从同一个运行时访问边界。

## 8. 简单用法直接，高级能力按需要出现

最短示例只包含完成任务必需的信息，并解释成功值与资源寿命。
第二个示例覆盖最常见的失败或可信 context；第三个例子才引入确有需要的组合、发布或嵌套资源。
不要让入门作者先学习所有内部 owner、lease、codec、transport 和版本机制。

调用方无需操作的复杂度可以封装在实现里；决定重试、权限、失效和关闭的复杂度必须从契约可见。
默认值可以减少选择，但须有单一权威实现。特殊输出或扩展点在真实消费者出现后提供，不预先做通用策略平台。

文档应有唯一的当前契约入口，提案与已实现用法分开。新增指南尽量链接已有事实，不复制另一份 API 说明。

## 9. 用真实任务决定是否增加复杂度

新抽象先做一条完整路径：定义、编写调用、实际执行、失败、清理。选包含真实权限或副作用的例子，不能只有 echo。
RPC、生成器与沙盒应分别证明其边界；上游库支持某项能力，不等于项目已经组合正确。

对“更高效”的判断，同时记录正确完成率、修复次数、文档查阅量、token、请求数和端到端时间。
固定模型、工具权限与任务条件，保留失败案例；不要以单次任务成功、少几个 token 或更少 HTTP 请求直接宣称总体更好。
正常路径更短但失败更难恢复时，应把代价算进去。

**引入机制的默认门槛：** 有具体调用方，现有入口确实不能表达，新增机制的职责可以一句话说清，且最小端到端验证已通过。
没有证据时先保持内部实现或实验状态，不把预留扩展变成兼容性承诺。

## 10. 一页设计评审记录

每次新增公开契约只需回答以下问题，不需要为所有小改动写长篇架构文档：

| 问题                                  | 需要的证据                                    |
| ------------------------------------- | --------------------------------------------- |
| 谁要完成什么任务，现有 API 卡在哪里？ | 一个真实调用点或可复现失败                    |
| 推荐的唯一默认写法是什么？            | 最短完整示例，包含必要的结果处理与清理        |
| 新概念多了什么真实职责？              | 状态、不变量、寿命或独立策略；没有则删除      |
| 哪些事实由谁维护，哪些可以推导？      | 输入、说明、实现、权限和输出的权威来源        |
| 类型能抓住哪些常见错误？              | 编译探针及需要运行时校验的明确边界            |
| 失败后调用方下一步是什么？            | 成功、预期失败、未知异常、部分成功/不确定结果 |
| 并发、取消、撤销和关闭如何发生？      | 对应时序和有风险的回归用例                    |
| 如何证明收益，何时停止扩展？          | 实际消费者、正确性条件、测量方法与未验证限制  |

符合项目惯例且行为简单的 API 可以用很短的答案通过；复杂边界则必须给出足够证据。
评审的产物应是一个可实现、可使用、可验证的契约，而不只是命名更漂亮的对象。
