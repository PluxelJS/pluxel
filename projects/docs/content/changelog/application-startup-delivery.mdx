## Let applications own production admission and entry points

Native and standalone applications now share preparation, graph startup, application
acceptance, entry-point publication and failure cleanup. Production startup rejects
unmet running intent by default with `HostApplicationStartupError`; applications can
explicitly accept partial availability through `acceptStartup`. Core and Vite retain
their existing partial-failure behavior. `launch` publishes the application's chosen
entry point only after acceptance, within the application's module identity.

Remove the build `launcher` option. Choose HTTP listening and `publicDir` in the
application's `launch` callback for both delivery modes. Standalone exports
`host`, `ctx`, `start` and `stop`, and preserves explicit application named exports;
it no longer manufactures `fetch` or `address`, installs an HTTP adapter, or enables
`public/` implicitly. The official launchers use this same application contract.

## Preserve HTTP response ownership and close the physical listener with its Host

Only an unhandled request can enter static-file or SPA fallback. Business, endpoint
and shell responses retain their status, headers and streaming body, including 404s.
The Node listener registers physical cleanup with root effects, so `host.close()`
and `listener.close()` share cancellation, draining and cleanup.

Pure HTTP applications can use the data-only `elysiaSharedPackages` export from
`@pluxel/services/sources`; Commands is an optional service peer. Standalone
`pluxel()` accepts and validates `managedDatabaseDrivers`, including an empty list
for applications that own their database. The headless delivery fixture exercises
the public build and runtime boundaries with libSQL and PDF streams.
