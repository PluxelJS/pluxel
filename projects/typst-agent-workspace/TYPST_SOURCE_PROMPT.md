# Typst 源码权威的报告编辑：下一轮实现 Prompt

这是可交给下一轮 coding agent 的任务说明，描述待验证的新设计，不代表当前 API 已实现。现有 Markdown 消费者与实测保留为对照；其提交为 `b5d010e9`。从下一节开始即可作为完整任务使用。

## 目标与范围

请在本仓库设计并实现一条 **Typst 源码为唯一正文权威、人和 Agent 共同编辑报告** 的路径。先检查现有能力与关键假设，说明最小设计，然后完成可运行的消费者实验与验证，不停在架构讨论或 AST 打印。

- `.typ` 文件保存正文、模板调用、原生 label/reference 和排版代码；业务数据保存到明确的 JSON 文件，图片等保存为资源文件。
- Agent 直接阅读、修改 `.typ` 和允许修改的 JSON；不要求先导出 Markdown，不把 Agent 编辑限定成另一种 DSL。
- Tiptap 是人的结构化编辑器。其 JSON、AST/CST、位置映射和引用索引都是当前源码修订的派生表示，可以重建；重新打开项目不能依赖隐藏的正文 JSON。
- 人的修改最终回写 Typst 源码。完整源码交给原有 Typst 编译链渲染；不从 PDF 或求值后的内容反推源码。
- 优先覆盖已有报告能力，尤其图表与题注、`<label>`、`@label` 补全、跨文件引用、改名、移动，以及数据绑定。
- 面向 Pluxel Typst 核心与独立消费者，不围绕 Studio 设计。实验应持久保存在仓库中，能提交、复跑；不只留临时脚本。

本轮目标是证明源码权威路径并形成足够小的核心契约，不顺带改造所有应用。旧消费者作为历史对照可以保留；同一份新报告不能同时维护 Typst 与 Tiptap JSON 两套权威。若最终替换已有公共契约，须同步真实调用方、文档与导出，不能把未迁移状态写成已完成。

遵守仓库 AGENTS、工程原则和相关 skills。优先复用现有能力；不要增加第二个 Typst 解释器、通用文档 AST、全局编辑 controller 或自制文件依赖语言。

## 优先核实并使用的解析库

优先验证 `@r4ai/typst-ast-node`，浏览器接入评估同项目的 `@r4ai/typst-ast-web`。不要把 Node 包直接打进浏览器。确认实际安装版本、导出、WASM 初始化、运行环境、错误返回及对应 Typst 语法版本。

```ts
import { parse, parseAst } from '@r4ai/typst-ast-node'

const source = '\n普通文字 #text(fill: red)[*重要事项*]\n'
const ast = parseAst(source, { mode: 'markup' })
const cst = parse(source, { mode: 'markup' })

console.log(ast.root, ast.errors)
console.log(cst.root, cst.errors)
```

2026-10-28 已在隔离目录运行 npm 发布的 `0.3.0`，未向本仓库添加依赖。以下是具体样本观察，后续应固定所选版本并转成必要的回归：

- 上述源码 JS 长度为 31，UTF-8 长度为 47；CST 根范围为 `[0, 47]`，函数调用 AST 范围为 `[15, 46]`，**不包含前面的 `#`**。
- `ast.root` 是表达式数组；不能假设所有表达式都有可用 range，类型允许 `null`。
- 中文、emoji、CRLF、注释、label/ref 和未闭合 content block 的五个小样本中，CST 叶子的 text 顺序拼接可还原原文；这不是任意源码保真的证明。
- AST 保留 label/ref 等结构信息，但不保留注释。语法错误样本仍返回树和 errors；有树不代表能安全结构化编辑或编译。
- 上游当前 `Cargo.toml` 声明 `typst-syntax 0.14.2`；本地 native 编译器的已构建 lockfile 也是 `0.14.2`，但后者使用 fork。同版本号不等于全部语法与行为兼容，需以实际样本验证。

来源：[上游项目与 API](https://github.com/r4ai/typst-ast)、[类型](https://github.com/r4ai/typst-ast/blob/main/src/types.ts)、[解析实现](https://github.com/r4ai/typst-ast/blob/main/src/lib.rs)、[语法版本](https://github.com/r4ai/typst-ast/blob/main/Cargo.toml)。发布物与源码不一致时，以所选发布物的实际行为为依据。

AST 用于识别支持的结构；CST、原始源码及其范围用于保真回写。解析库不求值、不解析业务数据、不自动建立可靠的全项目引用关系，也不保证增量解析或直接提供源码 printer。

## 需要收敛的设计

### 1. 权威存储与编辑事务

明确一条控制路径：读取源码快照 → 解析并投影到 Tiptap → 人的编辑事务 → 校验并生成源码补丁 → 接纳新的源码修订 → 更新投影与编译。

- 保存的是源码；派生 JSON 可以缓存但不能成为恢复项目的必需条件。JSON 数据拥有自己的事实，图表渲染值不能复制成第二份可写正文。
- 无操作打开/保存须保持源码字节不变。局部改字不得整文件重新排版；未编辑的注释、空白、参数、未知语法必须保留。
- 选择能保持语法完整的最小回写范围；允许必要时重写一个已支持的结构，但说明范围，并保留结构内部未编辑的未知源码。无法证明可保留时，明确拒绝该结构化操作并提供源码入口。
- 原始 UTF-8 范围、JS UTF-16 索引、Tiptap document position 和预览坐标分别处理。覆盖转义文本、emoji、组合字符、CRLF、相邻节点的 trivia 和 `#` 边界；不要全局使用 `source.slice(...ast.range)`。
- 每个补丁绑定文件与基线修订。外部 Agent 更新后，旧 Tiptap 事务必须明确冲突或基于可验证规则重建，不能按旧位置覆盖新文件。
- 源码修改、投影修改与 undo/redo 由一套明确的事务关系持有，避免两个独立历史互相覆盖。跨文件 label 改名也应是整体事务；原生 Tiptap history 不能未经验证就宣称支持项目级撤销。
- 编辑中的无效源码可以作为草稿保存并显示诊断；最后成功编译结果标明旧修订。区分草稿已保存、投影可编辑、编译成功，不用旧预览伪装当前源码成功。

### 2. Tiptap 支持范围与未知语法

先列实际支持矩阵，再实现。每种结构明确：是否结构化编辑、是否保留原文、如何写回、何时进入源码编辑、错误定位在哪里。

| 情况                                       | 期望行为                                                          |
| ------------------------------------------ | ----------------------------------------------------------------- |
| 已支持的段落、标题、列表、样式、手工表格等 | 原生 Tiptap 编辑，局部回写合法 Typst                              |
| 已声明模板组件或可识别的数据绑定           | 显示参数/绑定控件，修改明确的参数或数据源                         |
| 未知内联表达式                             | 在原位置保留源码，使用内联源码节点/入口，不吞掉两侧文字或强制断段 |
| 未知块、循环、复杂调用                     | 保留整段源码，显示可理解的源码卡片/入口；不把求值结果变成静态正文 |
| `let/import/set/show` 等环境语句           | 保持其顺序和作用域；不简单伪装成可随意拖动的普通正文块            |
| 语法暂时不完整或边界不确定                 | 保留原文和诊断，限制受影响范围的结构化操作，允许源码修复          |

未知结构保留到什么语法边界，须基于 CST 和实际上下文决定。移动未知块可能改变作用域或相对路径：只有明确支持的移动才开放；不能承诺保留字节便等于保留语义。

支持 `#text(fill: red)[*重要事项*]` 时，修改文字或加粗应保留外层调用。未知参数、计算属性也不能在保存时丢失。函数名可能被 shadow/import 重定义，不能仅见到 `text`、`figure`、`table` 就无条件认作内置函数；选择可解释、可验证的识别边界。

无需在富文本界面重现所有 `set/show` 的外观。实际排版继续以 Typst 预览为准；结构化编辑界面清楚区分显式属性与模板继承。

### 3. 报告能力，尤其 label 与 `@`

优先盘点并恢复现有的用户能力，不机械复制旧 JSON 字段：

- 基础正文、常用 Mark、链接、字体字号颜色与段落对齐、列表、代码内容。
- 手工表格、合并单元格、多段落单元格与已有表格样式；不能将整个已有表格都降为不可编辑源码后宣称能力保留。
- 图片、figure、富文本题注及公式；题注与对象一起移动，编号由 Typst 模板计算。
- 模板组件、业务字段与 JSON 数据驱动块；数据表与手工表具有不同的修改目标。
- `<fig:revenue>` / `@fig:revenue`、`@` 候选搜索、跨文件跳转、label 编辑、重复与缺失诊断、复制与移动。
- 引用的“跟随模板 / 仅编号 / 编号与题注”现有行为须设计对应的源码表达。原生 `@label[supplement]` 不应未经核实就当成旧 `showCaption` 的等价物。
- 当前公式是 LaTeX + MiTeX，原生 Typst 数学语法不同。保留现有 LaTeX 能力可以使用明确的源码调用；原生数学须保留。不要承诺任意 LaTeX ↔ Typst 无损互转。

引用设计要回答这些实际问题：

1. label 与其目标的归属如何确定？图片/表格/公式、相邻注释与空白、`#figure(...) <label>` 都要覆盖，不能简单绑到前一个 AST 节点就结束。
2. 源码中的 `@label` 是真实引用。UI 改名时，如何原子更新目标声明与项目中可确认的引用？跨文件权限或冲突如何避免部分改名？
3. 复制带引用的子树时如何生成不冲突的 label，并只重绑复制子树内指向所复制目标的引用？普通移动保持 label；跨文件移动另检查资源相对路径和作用域。
4. 源码权威后，旧隐藏 UUID 不再是引用唯一依据。优先使用原生 label 与修订内的位置；若确需额外持久身份，解释必要行为和存储方式，不暗藏第二份文档索引作为恢复前提。
5. `@key` 也可能是文献引用，模板可能在循环或函数中产生 label。静态索引只承诺可确认的目标，求值相关结果以真实编译为准；不把静态未命中一律报成缺失，也不全局正则替换字符串、注释或未知动态调用。

报告中本已支持的静态图表与引用必须真正可编辑；动态或无法确认的情形可以保留源码并明确能力边界。其他尚未恢复的功能列出缺口，不能把阶段性闭环描述为完整迁移。

### 4. 文件、模板与数据

建议保持普通 Typst 项目形态，文件名可据实现调整：

```text
report/
  main.typ
  template/layout.typ
  template/blocks.typ
  sections/analysis.typ
  sections/actions.typ
  data/sales.json
  assets/logo.svg
```

- 组合使用原生 `include/import`，不把所有文件展开成一份可写 Tiptap JSON；按源文件或明确片段打开编辑器。一个文件被多次 include 时，共享源码的修改含义必须明确。
- 项目内文件引用使用相对路径，并按 Typst 的调用文件上下文解析。允许目录内必要的 `../`，规范化后不得逃出项目；不能把“相对路径”误写成“禁止所有父目录段”。宿主绝对磁盘 root 和编译器内部虚拟路径另属一层。
- 数据文件、含义/schema、读写归属对 Agent 显式可见，Agent 可直接处理权威 JSON。避免为了“声明依赖”再复制一份全部 import 图；静态可见引用与动态实际读取的边界说清楚。
- 数据加载与校验策略应有一处所有者。若承诺只允许读取声明资源，须在实际资源读取边界落实，不能用正则扫描源码充当约束。
- JSON 更新后提交同一项目快照重编译，数据绑定、指标和真实数据图表自然重算；分析正文不自动改写。外部文件监听属于宿主，不能把 session API 描述成自带 watch。
- 现有 `session.update({ files })` 是完整文件表替换，遗漏文件会被移除，不是 patch API。模板与数据修改须进入一致的编译修订；不用局部文件表误删其他资源，也不用每次重建 Host/编译器来掩盖更新路径。

## 实施顺序与验收

先核实库与边界，给出简短的责任划分和功能矩阵，然后直接实现一个跨越真实边界的切片；不要先搭通用插件注册平台或大规模重写全部 UI。

第一条切片必须包含：两个正文 `.typ` 文件、一个模板、一个 JSON、一个真实数据驱动块、一个带 label 的 figure、跨文件 `@` 引用、一个未知内联表达式和一个源码块。使用现有公开 Typst 编译入口及真实 Tiptap Editor；消费者不 import 核心内部源码、不获取内部 Host 实例。

依次验证：

1. **Agent → 人 → Agent**：Agent 直接改正文 Typst 和 JSON；人通过 Tiptap 修改一段正文、题注并插入引用；保存后从磁盘重新打开，Agent 能读到对应源码修改。原始源码独立足以恢复项目。
2. **保真与未知语法**：无操作字节不变；编辑已支持内容不改变未触及源码。覆盖注释、空行、转义、Unicode、CRLF、`#`、嵌套调用与相邻未知节点。未知语法保持可修复，不能静默丢失或写成显示用代码围栏。
3. **引用整体性**：跨文件改名、移动 figure、复制含内部引用的子树；重复 label、删除目标及修改冲突给出可定位结果，失败不部分保存。检查最终 PDF 中实际编号和跳转。
4. **数据更新**：只改 JSON，真实图表/指标变化，模板和分析正文不被重写；不使用静态图片冒充动态数据图。数据与正文同批修改也能一致编译。
5. **编辑历史与并发**：人的修改可撤销/重做并重新打开；外部 Agent 修改后，旧 UI 操作不会覆盖新源码。跨文件重构的撤销范围如实验证。
6. **错误恢复**：无效 Typst 原文保留；错误可定位到文件和范围；修复后恢复结构化编辑与真实编译。旧预览不能被标为新修订成功。
7. **人的真实入口**：无 DOM Editor 验证模型之外，用实际浏览器界面验证至少一次中文输入、选区、`@` 补全、题注/label 编辑、未知源码修复、保存与重新打开。若环境限制无法验证，明确未验证边界，不以 JSON 断言代替。

沿这条路径补齐优先级中的既有报告能力，按风险增加必要回归；不要因为 parser 样本成功就宣称编辑器完成，也不追求用一轮实现覆盖任意 Typst 程序。

完成时交付：

- 一份简洁的最终设计：权威源、源码/投影事务、位置单位、未知语法、label/ref、模板/数据及运行环境边界。
- 可复跑的核心能力与独立消费者、依赖与构建接线、运行命令，以及实际源码 diff、PDF/预览证据。
- 基于现有功能的支持矩阵，区分结构化支持、仅保留源码、尚未实现与尚未验证。
- 有针对性的测试与真实编辑路径结果；说明删去了哪些旧转换环节、增加了哪些必要复杂度。单次小样本不外推 Agent 效率或任意项目的无损能力。

验证完成后停止在本轮范围内。不要顺带迁移 Studio、发布包、部署服务或推送；是否推广成现有主路径，依据这个实验的证据另行决定。
