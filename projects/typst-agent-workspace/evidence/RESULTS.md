## 对核心设计的反馈

1. **当前内容模型足以支撑这条路径。** 区域化原生 JSON、Agent Markdown 的语义往返和单向 Typst 生成已经组合成功。标准 Markdown 部分容易直接修改；图表包装完整移动后，稳定 id 引用继续成立。无需为这个场景再造一套正文 AST。
2. **文档级候选有明确价值。** 跨章移图要求先形成最终区域集合，再检查身份与引用。消费者目前自行组合单区域 `prepareTypstCandidate`、`validateTypstRegions` 和 `generateTypstRegions`；这是值得核心收敛的重复工作。文件 IO、锁、快照版本和正式存储仍由消费者持有。
3. **优先补 Markdown 来源诊断。** 错误能带稳定 code 和区域/JSON path，消费者可补文件名；尚不能直接给出 Markdown 行列。非法标记、组件参数或引用出错时，agent 仍需在文件里搜索。这个缺口比新增语法更直接影响修正成本。
4. **复杂块可保真，但首次规范化增加阅读噪声。** 编辑后的分析文件为 1,384 字节，保存后重新导出为 1,675 字节；其中原生块从 724 增至 999 字节，主要是稀疏初始 JSON 经 ProseMirror 接纳后补齐默认属性。再次往返保持字节稳定，并非每轮持续膨胀。可考虑在无损校验前提下省略 schema 默认属性、稳定序列化输出。
5. **模板参数的发现仍依赖消费者说明。** 本例的组件参数通过 Valibot 校验，但 agent 所读的 `title` 用法是作者写入任务文件的。将常用组件参数说明与可检查的定义统一，值得以此消费者继续验证；此次没有增加通用 schema 或工作区 API。

普通 Markdown 的复杂内容损失、非法组件参数、重复身份、缺失引用、陈旧基线、缺失区域和修改只读上下文均有回归。另一个用例验证：前一章合法、后一章非法时，已保存正文完全不变，错误候选仍留在磁盘。

## 验证边界

代码只通过 Typst 包公开入口加载构建制品；编译使用普通 Host 和 constructor DI，不依赖 Studio 或内部实例访问。依赖由当前仓库提供，未执行独立 registry 安装；字体和 native 平台只验证了当前 Linux 环境。

这是离线文件编辑消费者，未实现多人实时协作、自动三方合并、模板编辑 UI 或长期工作区同步。任务中的文件清单与提交接口是消费者实验契约，不是已经加入 Pluxel Typst 的公共 API。
